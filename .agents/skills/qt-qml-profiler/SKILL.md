# Qt Quick 性能调查

先读取适用的 `AGENTS.md`，明确用户遇到的操作、数据规模和观察指标。构建、产物位置、启动授权和进程管理遵守项目规则。

## 分析已有记录

用户给出 `.qtd` 时直接校验并解析，不为分析记录重新构建或启动应用：

```bash
python3 "<skill-dir>/references/scripts/parse-qmlprofiler-trace.py" "<trace.qtd>"
```

- 路径相对本 skill 解析。记录存在且可解析才继续；不能以文件必须大于某个固定大小作为有效性标准。
- 解析器非零退出或返回 `error` 时报告具体原因，不编造热点。
- 检查采集特性、场景、Qt 版本和是否中断；没有相应事件不代表该项开销为零。
- 记录中的源码可能不是当前工作区版本；定位前核对路径和对应版本。

## 需要新采集时

- 优先从已配置构建、Qt 路径和 PATH 找到匹配工具，使用该版本 `qmlprofiler --help` 核对参数。
- 先确定有限且可复现的场景，再决定绑定、JavaScript、创建、场景图、内存等采集范围。
- 检查现有可执行文件是否支持 QML 调试。需要启用时沿用项目配置入口，保留原编译参数，并防止调试选项残留到部署产物。
- 不为了启用 QT_QML_DEBUG 覆盖整个 `CMAKE_CXX_FLAGS`，也不自动创建仓库内构建目录。
- 采集通常会启动应用；先核对本轮授权及项目约束。若禁止启动，继续静态定位或分析已有记录，明确动态测量缺口。
- 无显示采集可以研究部分逻辑，但渲染后端与真机不同，不能替代真实 GPU 帧率结论。
- 手动交互采集先说明场景和结束方式；异步等待保持可汇报进度，不无限阻塞，也不擅自结束已有用户进程。
- 只结束自己启动且按约定可结束的采集进程，保留退出码；中断产生的部分记录须标明不完整。

核对当前工具参数后，典型命令形状为：

```bash
"<qt-bin>/qmlprofiler" -o "<trace.qtd>" -- "<executable>"
```

## 指标解释

- `range_events_total_ms` 是范围事件耗时之和，事件可能嵌套，不能当成实际总运行时间。
- 热点同时看总耗时、调用次数、单次成本和源码位置；绑定频繁不等于单次计算很慢。
- 脚本中的 `wall_ms_est` 和帧时百分位由记录的帧率样本估算，不是直接测得的每帧呈现时间。
- 内存分配统计不等于进程常驻内存或泄漏证据；pixmap 事件也不是完整 GPU 显存测量。
- 缺失指标写“未采集/不支持”，不填零；无法映射源码时保留原始事件位置。

热点解释按需读取 [性能检查点](references/qml-performance-anti-patterns.md)。解析字段以保留的 [解析脚本](references/scripts/parse-qmlprofiler-trace.py) 为准。

## 结论与验证

- 先给有证据的热点，再给源码支持的原因与最小改动建议；静态推测单独标明。
- 调查请求不自动授权重构；若同时要求优化，修改后用可比的场景和采集范围验证。
- 用户要求比较两次结果时可以比较，但先核对设备、构建、数据量和操作；条件不一致时说明限制。
- 默认回复关键指标和证据路径，只有用户要求或确有保存价值时写独立报告。
- 工具不可用或采集未完成时报告缺失环节，不能把静态检查写成性能测量完成。
