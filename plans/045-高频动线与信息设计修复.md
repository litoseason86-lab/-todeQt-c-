## 本轮被推翻的论证（含一条硬错误）

写下来是为了不再犯，也为了下一轮有人重新提出时能直接止住。

### 1. 「预设科目从不播种、新装科目下拉为空」——**完全错误，已撤回**

事实：`DatabaseManager::insertPresetCategories()`（[DatabaseManager.cpp:1338](../src/services/DatabaseManager.cpp#L1338)）
定义并播种 5 个预设科目（数学 / 英语 / 政治 / 专业课 / 其他，
常量见 [DatabaseManager.cpp:35](../src/services/DatabaseManager.cpp#L35)），
从 [line 283](../src/services/DatabaseManager.cpp#L283) 与 [line 540](../src/services/DatabaseManager.cpp#L540)
两处调用——**每次打开数据库都会跑**，靠 `display_order` 作稳定身份做幂等
（用户改名改色后不会再复制一行）。
测试 `freshDatabaseCreatesVersion4PresetCategories`（[ServiceTests.cpp:3711](../tests/ServiceTests.cpp#L3711)）
明确断言返回 5 条。

**错误根因（方法问题，不是看漏）**：原始调查跑的是
`grep -rn "is_preset" src/services/*.cpp | head -10`。该 grep 实际有 13 个命中，
被 `head -10` 截掉的恰好是 1342 / 1346 / 1416 三行——即证明播种存在的那三行。
然后从这份被截断的列表里断言了一个**全称否定**（「全代码库没有任何地方写过 `is_preset = 1`」）。

**规则**：不允许用带 `head` / `tail` 截断的输出去证明「代码库里不存在 X」。
要断言不存在，必须看完整输出，或先用 `| wc -l` 确认没有被截断。

### 2. 「热力色阶：学 1.5 小时和学 7 小时的差别比学 1.5 小时和完全没学还小」——**算术错误**

实测值是：全量程（90 分钟 → 420 分钟）亮度差 **32** 级；零投入 → 最低有效投入亮度差 **26** 级。
32 > 26，原结论与自己的数据相反。正确表述见阶段五，那里的问题是**绝对量程太小**，不是这个比较。

### 3. 「任务行的编辑/删除是悬停才浮现」——错误

`TaskItem.showEditDelete` 默认 `true`（[TaskItem.qml:87](../qml/components/TaskItem.qml#L87)），
两颗按钮常驻，悬停只改描边色。由此推导出的「等按钮浮现的等待成本」不存在。
零键盘导航那条独立成立，不受影响。

### 4. 「目标详情热力图只有两档色、0 分钟和 420 分钟同色」——走查工具自身的污染

离屏 harness 把整棵树上所有 `opacity === 0` 的项强设成 1，正好把热力图里
「零投入」格子的着色层拉满。凡是用 opacity 表达**数据强度**的组件都会被这么污染。
改用加长等待让入场动画自然跑完即可。

### 5. 「深色主题下周末列是两条抢眼的亮柱」——错误

实测周三空列 `(49,47,48)`、周六空列 `(45,43,42)`，周末列是**更暗** 4 个色阶，差异约 2%。
与 043 计划记过的结论一致，是 [ScheduleGrid.qml:475](../qml/components/ScheduleGrid.qml#L475)
刻意压到 0.22 的结果，**按设计工作，不要改**。

### 6. 「新建任务后按标题反查就能拿到它」——身份契约错误（实施期，用户指出）

标题不是唯一键，同一天允许同名任务；反查只能在一堆同名任务里挑一个，
挑错的后果是这段专注记到别人头上且看不出来。补一条「查不到就报错」也不管用，
那只防漏查、防不了误匹配。已改为服务层返回新任务编号，见阶段一「新建任务的身份契约」。

**根因是把计划的落点清单当成了不能越界的围栏**：正确做法是加接口、在落点表里补一行，
而不是在调用方拼一个凑合的查法。落点清单是范围说明，不是绕开正确接口的理由。

### 7. 「5 档收益变薄，所以取 4 档」——指标用错（第二轮出稿时自查，用户指出）

用相邻档亮度差（`0.299R + 0.587G + 0.114B`）去否决 5 档。亮度差只说明色阶在明度上拉开了，
不回答「相邻两档分不分得出」，也不回答「格子上的日期读不读得出来」——
而这两件事正是本阶段自己列的必答问题。换成 CIEDE2000 与 4.5:1 重算后，
**5 档同样做得出来**。取 4 档的真实理由是版面分组，不是度量结论。详见阶段五。

### 8. 「⌘⇧K 是因为 ⌘⇧N 被现有测试占用」——理由错误（只出现在实施后的交付说明里）

测试占用某个键位，不构成产品改键的依据；方向反了——该改的是测试。
`gap.capture` 取 ⌘⇧K 的正当理由只有两条：**交互约定**（⌘⇧N 是「新建任务」的近邻，
两者产物完全不同，挨在一起诱导按错）与**冲突检查**（⌘⇧K 在默认表里空着）。
测试侧已改为统一使用一个永不会成为产品默认值的样本键，见阶段二边界。

## 阶段一：专注页任务选择器，并统一「开始专注」的口径

### 证据

同一个概念动作，三处行为不一致：

| 入口 | 空闲时的行为 | 位置 |
| --- | --- | --- |
| 仪表盘「开始专注」 | 捡 `root.tasks` 里第一个未完成任务并启动 | [DashboardView.qml:316-325](../qml/views/DashboardView.qml#L316-L325) |
| 专注页「开始专注」 | 没选任务时 `enabled` 为假，点不动 | [FocusView.qml:506-520](../qml/views/FocusView.qml#L506-L520) |
| ⌘↩ / 全局热键 | 切到专注页 + 弹「请先选择要专注的任务」 | [MainWindow.qml:551-553](../qml/MainWindow.qml#L551-L553) |

而**专注页没有任何选择任务的控件**：`selectedTaskId` 在 `FocusView.qml` 里有 8 处赋值，
全部来自计时器回写或今日页传入的 `startFocus` 信号，用户无法直接设置它。

于是 ⌘↩ 和全局热键在空闲时是**死路**：它把你送到一个明确要求你做某件事的页面，
而那件事在那个页面上做不到。

### 候选口径（已定值，实施照此执行）

以下为本计划的定值，不是待确认的建议。要改需先改本表。

| 问题 | 取值 | 理由 |
| --- | --- | --- |
| 候选来自哪里 | `TaskManager::getTodayTasks()`，即**逻辑今日**的任务 | 与仪表盘现有口径一致（它读的就是 `getTodayTasks()`，[DashboardView.qml:246](../qml/views/DashboardView.qml#L246)），不是「全部未完成任务」 |
| 已完成任务是否可选 | **可选**。列出但置于末尾、默认不选中；当前计时绑定的那条即使已完成也必须在候选里 | 与补录候选「被编辑记录的原归属任务始终出现在候选中」同构，否则切页回来会被静默改成别的任务。另外「今天的任务都做完了，但我还想再练一轮」是真实场景，不应堵死 |
| 是否提供「不关联任务」 | **不提供** | 现状 `canStartFreeFocus()` 要求 `selectedTaskId > 0`，实时计时必须绑任务。统计里的「未关联专注」来自补录与历史数据，不是实时路径。**不要照搬 [ManualSessionDialog.qml:49](../qml/components/ManualSessionDialog.qml#L49) 的 `taskOptions`**——它首项恒为「不关联任务」，且候选来自历史服务、按所选日期就近排序，用途是补录不是实时专注 |
| 自动启动取哪一条 | 已有有效 `selectedTaskId` 时**优先用它**；否则取今日**未完成**任务里 `display_order` 最小的那条 | 用户刚在今日页点过某条再按 ⌘↩，不应该被改成别的任务 |

### 没有可自动启动的任务时（唯一的兜底分支）

上一版把「今日零任务」单独列了一条，**漏掉了「今日有任务但全部已完成、且没有有效选中项」**——
这种状态既没有未完成任务可自动启动，也不满足「零任务」的条件，会掉进一个没有规则覆盖的空分支。

因此不按「今日有没有任务」分叉，**只按「有没有可自动启动的任务」分叉**，两种情况合并成一条规则：

> 按上表取不到可自动启动的任务时（今日零任务、或今日任务全部已完成，两种情况同等对待）：
> 切到专注页，**展开选择器**。选择器里既可以选已完成的任务再专注一轮，
> 也可以用内联入口新建今日任务并开始。

**不允许出现「聚焦一个什么都选不了的空选择器」这种终态**——那仍然是死路，只是换了个位置。

### 改法

1. 专注页加常驻任务选择器：空闲态为可点击选择器，计时中为静态标题。
2. `toggleFocusFromShortcut()` 空闲分支按上表口径自动启动；
   **取不到可自动启动的任务时**（零任务与全部已完成同等对待）才切页并展开选择器。

### 新建任务的身份契约（2026-09-13 实施后补）

选择器里「新建今日任务并开始」建完就要立刻把计时绑上去，因此必须拿到新任务的编号。

原有 `TaskManager::addTask` 全部只返回 `bool`。第一版实现绕开了这件事：建完重拉今日任务，
取「标题相同、未完成、`display_order` 最大」的那条。**这是错的，已改掉。**
标题不是唯一键——同一天允许同名任务，反查只能在一堆同名任务里挑一个；
挑错的后果是这段专注记到了另一条任务上，界面上完全看不出来。
它的正确性还挂在另一个模块的内部不变量（`display_order = 当天最大值 + 1`）上，
那个不变量没有任何东西强制或测试。加一条「查不到就报错」也不解决问题：
那只防漏查，防不了误匹配——错在选了一个本就不唯一的键。

**计划里的落点清单是范围说明，不是绕开正确接口的理由。** 需要新接口就加新接口，
在落点表里补一行，而不是在调用方拼一个凑合的查法。

因此服务层新增 `TaskManager::createTask(...) -> int`：成功返回新任务编号，失败返回 `-1`。
四个 `addTask` 重载改为以它为实现（`return createTask(...) > 0`），行为不变。
插入成功却读不出编号时照常发 `tasksChanged`（行确实写进去了），但返回 `-1` 让调用方按失败处理，
**绝不返回一个猜来的编号**。

### 落点

| 文件 | 改动 |
| --- | --- |
| `src/services/TaskManager.h` / `.cpp` | 新增 `createTask` 返回新任务编号；`addTask` 改为委托 |
| `qml/views/FocusView.qml` | 新增任务选择器；`selectedTaskId` 增加用户可写路径 |
| `qml/MainWindow.qml` | `toggleFocusFromShortcut()` 空闲分支 |
| `tests/ServiceTests.cpp` | `createTask` 的编号契约与同名任务区分 |
| `tests/qml/tst_focus_start_flow.qml` | 补用例 |

### 验收

- 空闲态在专注页能直接选任务并启动，全程不离开专注页。
- 有今日未完成任务时按 ⌘↩ 直接开始计时，不再出现「请先选择要专注的任务」。
- 已有 `selectedTaskId` 时 ⌘↩ 启动的是它，不是列表第一条。
- 计时进行中按 ⌘↩ 仍是暂停/继续（回归）。
- 当前绑定任务被标记完成后，它仍出现在候选里且保持选中。
- 新建任务后计时绑定的是 `createTask` 返回的那条：今天已存在同名未完成任务
  （且 `display_order` 更大）时，绑定的仍是新建的那条。
- `createTask` 返回 `-1` 时不启动任何计时，并给出错误提示。

兜底分支的三条（**这三条是一组，只测其中一条抓不到那个空分支**）：

- 今日零任务 → ⌘↩ 后选择器展开，且「新建今日任务并开始」可用。
- **今日有任务但全部已完成、且无有效选中项 → ⌘↩ 后选择器展开，已完成任务可选中并启动，也可新建。**
- 以上两种状态下都不存在「按了但什么也没发生」的终态。

### 边界

- 不改 `FocusSessionRules`，不碰有效番茄与有效时长口径。
- 切换活动任务仍走既有确认流程（[FocusView.qml:414-464](../qml/views/FocusView.qml#L414-L464)），不得绕过。

## 阶段二：知识缺口捕获加键盘入口

### 证据

[KnowledgeGapCapturePopup.qml](../qml/components/KnowledgeGapCapturePopup.qml) 的设计意图写在注释里：
「捕获一旦需要做决策，人就懒得记了」。弹窗本身做到了——非模态、一行字、回车存下。

但两个入口全是鼠标按钮：专注页右上角那颗（按 2026-09-11 保持决策**常态透明、悬停才出玻璃底**），
和今日任务页页头的「记一笔」。[ShortcutRegistry.cpp](../src/services/ShortcutRegistry.cpp) 的 18 个动作里没有捕获。

真实场景是「在别的窗口做真题，发现一块不懂」，此刻应用在后台。
当前代价是 ⌘Tab → 切页 → 找一颗常态看不见的按钮 → 点击 → 打字，
已经超过「算了回头再说」。

### 改法

`ShortcutRegistry` 动作表新增 `gap.capture`（应用内）与 `global.captureGap`（全局热键，
走既有 Carbon 通道，出厂同样不占用任何系统按键）。触发后打开捕获框并聚焦输入框。
在专注页触发时带来源任务与科目，其它页面不带来源——与现有两个入口规则一致。

### 需要明确处理的三件事（上一版缺）

1. **后台窗口激活**：全局热键在应用位于后台时触发，是否把主窗口拉到前台？
   建议：**拉到前台并聚焦输入框**。捕获框是 `Popup`，依附窗口，不激活窗口就收不到键盘输入。
   若将来要做不激活窗口的捕获，那是独立面板，属另一个需求，不在本阶段。
2. **输入焦点**：`Popup.focus` 已为 `true` 且 `onOpened` 会 `forceActiveFocus()`。
   但从后台激活窗口存在时序问题——窗口激活与 Popup 打开的先后要显式确定，
   不能依赖 `Qt.callLater` 撞运气。
3. **与沉浸模式、弹窗让路规则的关系**：弹窗接管焦点时应用内快捷键整体让路（现有规则）。
   捕获热键在别的弹窗打开时应当**不触发**，与现有让路规则一致。

### 落点

| 文件 | 改动 |
| --- | --- |
| `src/services/ShortcutRegistry.cpp` | 动作表新增两条 |
| `qml/MainWindow.qml` | `dispatch` 新增分支；捕获框提升或加转发入口 |
| `tests/ShortcutRegistryTests.cpp` | 动作表断言 |
| `tests/qml/tst_knowledge_gap_capture.qml` | **快捷键集成用例**：走 `dispatch` 而不是直接调 `openWithSource` |

### 验收

- 应用内按下 `gap.capture` 键位，捕获框打开且输入框已获焦点，回车即存。
- 计时进行中触发捕获，计时**不暂停**（硬约束）。
- 全局热键在应用位于后台时可触发，窗口前置后输入框可直接打字。
- 其它弹窗打开时捕获热键不触发。
- 出厂不占用任何系统按键。

### 边界

**不违反 2026-09-03「切页快捷键只覆盖 8 页」那条保持决策**——那条说的是
`view.schedule` / `view.todayFocus` / `view.knowledgeGaps` 三个**切页**动作不加。
本阶段加的是捕获动作，不是切页动作。

**默认键位的理由只有交互约定与冲突检查两条，测试不参与。**
`ShortcutRegistryTests` 里那几处「随便换一个键位」的用例统一用 `kSpareSequence`
（`Ctrl+Alt+Shift+Y`，三修饰符 + 字母，不在默认表里，也不会成为任何产品默认值——
应用内默认一律 ⌘ 或 ⌘⇧ 打头）。用真键当样本会让以后给新动作定默认键位时撞红这些用例，
看起来却像「那个键不能用」。冲突与默认值本身由
`assignRejectsConflictWithAnotherActionInAnyScope` 和 `resetAllRestoresEveryDefault` 专门覆盖。

## 阶段五：热力色阶改离散档（先出对比稿，不直接落地）

### 证据（已更正）

是算术错误：32 > 26。已更正。）

根因**不在** [GoalHeatmap.qml:96](../qml/components/GoalHeatmap.qml#L96) 的
`0.25 + 0.75 * count / maxCount`——公式没错。根因是端点选错了：
`Theme.accent`（焦糖）与 `Theme.surfaceSunken`（`#f5ede3`）本身亮度接近，
再怎么调 opacity 都拉不开。这是配色问题，不是参数问题。

### 对比稿必须回答的问题（上一版全部缺失）

1. **分档数与阈值**：3 / 4 / 5 档各出一稿。阈值按什么定？两个候选：
   - **(a) 相对当月最大值的比例**，即现状 `count / maxCount` 的分档版。
     注意这是「占当月最大值的比例」，**不是百分位数/分位数**——它不看数据分布，
     只看和最大那天的比值（上一版误写成「百分比分位」，是术语错误）。
   - **(b) 绝对分钟数固定阈值**（如 <60 / 60–150 / 150–300 / >300）。

   两者行为差别很大：(a) 在「整月都学得少」时仍会把最高那天染成最深，
   (b) 则如实反映「这个月整体就是低」。**这是产品取舍，必须先定。**
2. **全零月份**：`maxCount = 0` 时的表现（当前 `intensity` 为 0，不会除零，但要确认新实现同样安全），
   以及界面上是否与「未来月份」区分。
3. **各档上的文字颜色**：现状是 `intensity > 0.55` 时切 `accentForeground`，
   改分档后这个门槛失效，每一档都要显式指定文字色并核对 4.5:1。
4. **两套主题**：浅色与深色各一组色阶。

### 第一轮对比稿（2026-09-13）与它的错误

已渲染四方案对比（现状 / 3 档 / 4 档 / 5 档），同一个月 0–480 分钟，日间与夜间各一张。
当时只测了一个指标——相邻档的亮度差（`0.299R + 0.587G + 0.114B`）：

| 方案 | 色阶 | 各档亮度 | 最小相邻差 |
| --- | --- | --- | --- |
| 现状 | accent 连续 opacity | 212 → 180（全量程） | **3** |
| 3 档 | `#f0e2cd #d9a566 #9c5a1e` | 228 / 173 / 103 | 55 |
| 4 档 | `#f3e8d8 #e2b881 #c07f38 #8a4d15` | 233 / 190 / 138 / 89 | 43 |
| 5 档 | `#f5ede3 #e8c9a8 #d49b63 #b5702f #8a4d15` | 238 / 207 / 166 / 125 / 89 | 31 |

当时据此建议取 4 档，理由写的是「5 档最小差 31 已接近现状的全量程差（32），再分一档收益变薄」。
**这条理由无效，已撤回。** 亮度差只能说明色阶在明度上拉开了，
它既不等于「相邻两档人眼分得出」，也不等于「格子上的日期读得出来」——
而本节开头自己列的四个必答问题里，第 3 条（各档文字 4.5:1）和第 4 条（两套主题）
恰恰就是这两件事。拿一个不回答这些问题的指标去否决 5 档，是用错了尺子。

### 第二轮：补上真正的两把尺子（2026-09-14）

- **文字对比度**：WCAG AA 正文 **4.5:1**。格子中央是日期数字（11px），
  [GoalHeatmap.qml:150-161](../qml/components/GoalHeatmap.qml#L150-L161)，不是可选项。
  每一档取 `Theme.inkStrong`（`#3d3327`）与 `Theme.surface`（`#fffef9`）里较优的那个。
- **相邻可辨识**：**CIEDE2000 色差 ΔE00**。经验刻度：≥5 不用并排比也看得出不同，
  2–5 并排能看出、隔开未必，<2 接近同色。零值格与第一档同样要过这一关——
  「学了一点」和「完全没学」看起来一样，是比档位少更严重的问题。

按这两把尺子复核第一轮的三张稿：

| 原稿 | 文字 4.5:1 | 零值格 → 第 1 档 ΔE00 | 结论 |
| --- | --- | --- | --- |
| 3 档 | 全部通过（9.68 / 5.60 / 5.34） | **5.0**（勉强） | 勉强可用 |
| 4 档 | **第 3 档 `#c07f38` 只有 3.72:1** | **2.7** | 不可用 |
| 5 档 | **第 4 档 `#b5702f` 只有 3.91:1** | **0.0**（第 1 档就是零值格本身，同一个 `#f5ede3`） | 不可用 |

两条都是第一轮完全没看见的：建议采用的那张 4 档稿有一档的数字读不出来，
而它的第一档和「没学」几乎同色。**第一轮的色值不能用，全部重做。**

### 约束：在**这组文字色**下，中间那段亮度用不了

每档只从两个文字色里二选一——浅色主题是 `#3d3327`（`Theme.inkStrong`）与
`#fffef9`（`Theme.surface`），深色主题是 `#f3ead9` 与 `#2a241c`。
在这组取值下，深字要到相对亮度 ≳0.33 才够 4.5:1，浅字要到 ≲0.17，
中间 **0.17–0.33** 两种都不达标；深色主题同理，禁区是 **0.14–0.26**。

**结论只到这里为止：在当前文字色与暖色方案下，要同时满足对比度就得非等距取色。**
这不是色阶本身的性质——禁区是这组文字色算出来的，换一组（例如给中间档单独配一个文字色，
或在色块上加描边/半透明衬底）禁区会移动甚至消失。不要把它推广成
「多级色阶不可能等距」，那是从一组具体取值跳到普遍命题。

本轮没有去动文字色：多加一个中间文字色意味着同一张图上出现三种字色，
在 38px 的格子里更像杂色而不是层级。这是**本轮的选择**，不是被证明唯一可行的做法。

### 定稿候选（2026-09-14，两套主题，4 档 + 绝对分钟阈值）

阈值按用户已定的方向取绝对分钟数，**两页共用同一套规则**（本阶段与阶段六）：

| 档 | 投入 | 日间色 | 日间文字 | 夜间色 | 夜间文字 |
| --- | --- | --- | --- | --- | --- |
| 零值 | 0 | `Theme.surfaceSunken` | `Theme.inkMuted` | `Theme.surfaceSunken` | `Theme.inkMuted` |
| 1 | < 60 分钟 | `#f1d9c4` | `#3d3327` | `#5e4123` | `#f3ead9` |
| 2 | 60–149 | `#e1a161` | `#3d3327` | `#825b34` | `#f3ead9` |
| 3 | 150–299 | `#855d36` | `#fffef9` | `#d09459` | `#2a241c` |
| 4 | ≥ 300 | `#52381e` | `#fffef9` | `#edccaf` | `#2a241c` |

**两套主题方向相反是刻意的**：浅底上「投入越多越深」，深底上「投入越多越亮」。
第一轮夜间那张之所以整个反了（最低档几乎是白块、比高投入还抢眼），就是直接套用了日间那套。
两套取自同一条暖色轴（Lab 色相 68°，彩度取该明度下色域上限的 0.55），
只是各取一段、方向相反，所以两套的色相仍与 `Theme.accent` 的焦糖一致。

实测（离屏渲染后按像素复核，稿见 `shots/heat2_light.png` / `heat2_dark.png`，**未进仓**）：

| | 各档实测色 | 文字对比度 | 相邻 ΔE00（零→1 起） |
| --- | --- | --- | --- |
| 日间 | `#f5ede3` `#f1d9c4` `#e1a161` `#855d36` `#52381e` | 9.09 / 5.57 / 5.75 / 10.70 | 7.6 / 17.9 / 26.5 / 14.4 |

### 4 档还是 5 档：原来的理由没了，结论仍取 4 档

按新尺子重算，**5 档同样做得出来**（日间 `#f1d9c4 #dd9e60 #825b34 #5e4123 #3b2816`，
档间最小 ΔE00 9.8、零值格 → 第 1 档 7.6；夜间 `#553a20 #825b34 #bf8851 #e6ae79 #f1d9c4`，
档间最小 11.2；两套文字最低分别是 5.37:1 与 5.01:1）。所以「第五档收益薄」不成立——**是测错了，不是 5 档不行**。

真实的取舍变成这样：禁区把可用亮度切成两段，5 档必须往其中一段塞三个，
于是那三档挤在同一侧（日间是三个深棕、夜间是三个浅色），
在 38px 的格子上读起来像一组而不是三级。4 档正好两段各两个，分组清楚。
**这是版面判断，不是度量结论**；用户已选 4 档，按 4 档出稿，5 档的色值一并记在这里备查。

### 零值、今日与未来：逐格按日期判，不看整月（2026-09-14 用户定案）

**不存在「全零月份」这个状态**。是否零投入、是不是今天、有没有到，都是逐格判断，
按项目的**逻辑今日**（`LogicalDay`，默认 4 点日界）比较，不能用 `new Date()` 直接比。

| 格子 | 表现 | 语义 |
| --- | --- | --- |
| 过去 · 零投入 | 零值底色（`Theme.surfaceSunken`），日期用 `Theme.inkMuted` | 无投入 |
| 今日 · 零投入 | 零值底色 + 今日标记（已有的 `Theme.accent` 描边） | 今日暂无投入 |
| 今日 · 有投入 | 对应档底色 + 今日标记 | 正常显示当天档位 |
| 未来 | **不填色**，只留一圈 `Theme.border` 实描边，日期 `Theme.inkMuted` | 尚未到来 |
| 本月之外 | 完全空白（现状不变） | 不属于本月 |

**为什么不填色**：任何填色都会被读成投入量刻度上的一个点，于是「还没到的日子」
看起来像「那天没学」——这张图是给考研的人每天看的，把未来染成「没完成」是纯粹的负担。
空心格不在刻度上，读者一眼就知道它不参与比较。

**但让未来格被看见的信号是那圈描边，不是「没填色」。** 出稿时实测：
零值格的填充（`Theme.surfaceSunken`）在页面底色上只有 ΔE00 **4.8**，夜间 **2.6**——
单靠「填了没填」根本分不开过去零投入与未来。所以描边的强度是这个方案的地基，
三种做法并排比过（稿里第三行）：

| 做法 | 描边 vs 页面底色 ΔE00（日间 / 夜间） | 判断 |
| --- | --- | --- |
| A 细描边 `Theme.borderSubtle` | 8.1 / **5.1** | 夜间勉强，在整片月历里容易糊掉 |
| B 实描边 `Theme.border` | 9.8 / **11.1** | **取这个**，两个主题都稳 |
| C 不画格子、只留日期 | —（没有描边） | 区分最强，但月历右下角整片塌掉，网格形状没了 |

未来格与「本月之外」也要分得开：后者完全空白、连描边都没有。

**零值格很弱是对的，不用修**（2026-09-14 用户定案）。实测它在页面底色上只有
ΔE00 4.8、夜间 2.6，这不是本轮引入的，`GoalHeatmap` 现在就是这样。

出稿时我把这件事写成「未来比零投入显眼，信息价值反了」，**这条推理不成立，已撤回**：
热力图首先要突出的是投入强度，零值保持安静本来就合理；未来描边只负责说明
「尚未发生」，不需要和零值按信息价值排序。而且零投入那天的**日期数字与位置都还在**，
它没有变成一个缺失的日子——弱不等于丢失。

本轮**保留零值填充，不加描边，不动全局 `Theme.surfaceSunken`**。
真实使用中若确实认不出零值，做法是加一个专用的 **`heatmapZeroBackground`** 令牌，
而不是去调下沉背景——`surfaceSunken` 还被输入框和次级容器用着，为一张图牵动全应用是错的。

仍要知道的是：过去零投入与未来的区分**落在未来格那圈描边上**，
将来若有人把它调细，这两种状态会合并，夜间尤其明显。

读屏与悬停提示同样按这四种语义分别给词（「无投入」「今日暂无投入」「尚未到来」），
不要都播成「0 个番茄」。现有 `accessibilityName` 只分了「无投入 / N 个番茄」，需要扩。

## 阶段七：本周计划列表键盘导航

> 用户审核判定：补完整导航模型与验收后执行。本节已补，但仍是七个阶段里最需要先做设计的一个。

### 证据

`TodayTaskView.qml` 与 `WeekPlanView.qml` 里 grep 不到任何 `Keys.` / `currentIndex` / 键盘导航；
[TaskItem.qml:581-583](../qml/components/TaskItem.qml#L581-L583) 唯一的按键处理在改名输入框内部。
每天 10–15 条任务 ×（完成 + 开始 + 偶尔编辑）≈ 30–50 次鼠标横跨窗口。

### 导航模型（上一版缺，是主要执行缺口）

**简单加 `currentIndex` 行不通**：[WeekPlanView.qml:464](../qml/views/WeekPlanView.qml#L464) 的外层
`ListView` 是 `model: 7`，一项等于一天，任务在内层 `Repeater` 里。
`currentIndex` 选中的是**天**，不是任务。

需要一个显式游标，而不是复用 `ListView.currentIndex`：

| 项 | 规则 |
| --- | --- |
| 游标 | `(dayIndex, taskIndex)` 二元组，或在页面层维护一份扁平化的 `(day, task)` 序列 |
| ↑↓ | 在扁平序列上移动，**跨日连续**：周一最后一条按 ↓ 到周二第一条 |
| 空日 | **跳过**，不能停在没有任务的日子上 |
| 完成后重排 | 任务完成会让它在当天内下沉。焦点**跟随该任务**移动到新位置，不留在原下标 |
| 删除后 | 按固定链依次尝试，取第一个命中的：**当天后继 → 当天前驱 → 后续非空日首条 → 前序非空日末条 → 清空游标**。上一版只写了「当天下一条 / 下一个非空日首条 / 全周为空则清空」，漏掉两种常见情形：删掉当天最后一条但当天仍有前序任务（应落到前驱，而不是跳去别的一天），删掉全周最后一条但前几天仍有任务（应落到前序非空日的末条，而不是清空） |
| 滚动定位 | 游标移出可视区时把它滚进来。外层是虚拟化列表（`cacheBuffer: 180`），屏幕外 delegate 不存在，**不能靠累加 delegate 高度定位**，要用 `ListView.positionViewAtIndex` 配合日内偏移 |
| 刷新 | `refresh()` 会重建 `weekTasks`。按**任务 id** 恢复游标，不按下标——按下标会在任务增删后选中另一条 |
| 焦点环 | 复用 `Control.visualFocus`（见[业务规则](../docs/业务规则.md)），不用 `activeFocus` |

### 键位

↑↓ 移动、空格完成、⏎ 开始专注（仅今天那一行可用，与 `showStartFocus: dayRow.isToday` 一致）、
E 编辑、⌘⌫ 删除。

### 验收

- ↑↓ 能从周一第一条连续走到周日最后一条，中间的空日被跳过。
- 在某条上按空格完成后，焦点仍在**同一条任务**上（它已下沉到当天末尾）。
- 删除一条后，落点按「当天后继 → 当天前驱 → 后续非空日首条 → 前序非空日末条 → 清空」逐级命中。
  这五级要各有一条用例，**尤其是「当天最后一条但当天有前驱」与「全周最后一条但前几天有任务」这两级**
  ——它们正是上一版漏掉的，只测首尾两级抓不到。
- 游标移出可视区时列表自动滚动到它，滚动后再按 ↑↓ 落点正确（虚拟化下不偏移）。
- `refresh()` 后游标仍指向同一个任务 id。
- 非今天的行上按 ⏎ 不启动计时。
- 焦点在改名输入框时，空格与 E 不被抢走（沿用现有输入框让路规则）。

### 边界

- 本轮**只做本周计划页**。今日任务页的同类改动留到用户解禁后再提。
- **不与「侧栏顺序去掉 ↑↓ 按钮」那条保持决策冲突**——那条说的是设置页排序控件的按钮，
  不是列表的键盘选中。

## 验证

`ctest` **不会自动重新编译 C++**。改过 C++（阶段二会改 `ShortcutRegistry`）之后直接跑 ctest，
可能跑的是旧测试二进制却报告通过。每个阶段落地后按顺序执行：

```bash
# 1. 配置（首次，或 CMakeLists 变动后）
/Users/zerionlito/Qt/6.10.3/macos/bin/qt-cmake -B ~/pt-audit -S . \
    -DCMAKE_BUILD_TYPE=Release -DPOMODORO_TODO_DEPLOY_LOCAL=OFF

# 2. 构建（每个阶段都必须跑，且必须成功）
cmake --build ~/pt-audit -j8

# 3. 全量离屏回归
ctest --test-dir ~/pt-audit --output-on-failure --timeout 240 -j8
```

`POMODORO_TODO_DEPLOY_LOCAL=OFF` 是 cache 变量，会持久化，因此**必须用 `~/pt-audit` 这个独立目录**，
不能和部署用的 `~/pt-build` 混用。

### 第 2 步的验收标准

**标准是「构建成功」，不是「日志里出现 `Building CXX`」。**
上一版把每个阶段都绑到这行日志上，不成立：纯 QML 改动可能只重新打包资源不编译任何 C++，
正常的增量构建本来也可能无需编译。把它写成通用门槛，会让人在一次合法的空编译上误判成出了问题。

分两种情况：

- **任何阶段**：第 2 步必须执行且返回成功。不能因为「这轮只改了 QML」就跳过——
  QML 测试确实从源码解析（改 `.qml` 不必重新编译 C++ 就能跑 `tst_*.qml`），
  但**这不等于应用资源包不需要构建**，跳过第 2 步会让 ctest 里依赖资源清单的条目
  （如 `QmlResourceManifestTests`、各 Assets 测试）跑在旧资源上。
- **改过或还原过 C++ 时**（阶段二会改 `ShortcutRegistry`）：额外确认**对应目标真的重新编译了**。
  做变异验证尤其要确认——用 `cp` 还原源文件会让 mtime 变旧、make 直接跳过重编译，
  于是「还原后复跑」跑的仍是变异后的二进制，结论完全反过来。
  还原后 `touch` 该文件，并在输出里确认那个目标被重新编译（`plans/` 里已记过两次这个坑）。

外观类改动（阶段五、六）先出离屏对比稿，看过稿再定，结果记入 `plans/README.md` 的「保持的决策」。
