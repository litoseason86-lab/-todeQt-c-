## 背景

- `src/main.cpp`（522 行）同时做了四件事：创建业务对象，连接跨服务信号，按平台装配同步和系统能力，装 QML 引擎或 SwiftUI 根视图。
  文件里有 25 处 `QObject::connect`、30 处 `setContextProperty`，Mac 与 iOS 的代码用 `#if` 交错在一起。
- 服务层没有构建边界：二十多个测试目标各自重列一遍 `src/services` 的源文件，例如 `SyncControllerTests` 列了 26 个 `.cpp`。
  QML 和 Quick 的依赖会不会混进业务层，现在没有任何检查。
- 目标架构已经定稿：PTCore 和 PTApp 是平台无关的 C++ 核心与装配层，PTQml 是 QML 接入层，Mac 与 iOS 各自有入口。
  iPhone 原生界面、iOS 系统扩展都建在这个基础上。本计划只做基础这一步。

## 启动时序约束（任何阶段都不可违反）

入口里的启动顺序固定如下，057-B、057-C 搬代码时只能整段照搬，不能调换：

1. `QQuickStyle::setStyle("Basic")`，在创建 `QGuiApplication` **之前**；
2. 创建 `QGuiApplication`；
3. 注册打包字体；
4. `McpPaths::applyApplicationIdentity()`，设置组织名与应用名；
5. `setApplicationVersion`；
6. Mac：偏好域清理（会读 `QSettings`）、单实例守卫（会解析 `AppDataLocation`）；
7. 打开数据库。

- 第 4 步之前，不得读写 `QSettings`、解析 `QStandardPaths`、打开数据库。漏掉或推迟第 4 步时，应用名恰好仍是可执行文件名 `PomodoroTodo`，看不出异常，但组织名是空的。后果分两种：
  - **偏好域**：`QSettings` 按组织名与应用名确定偏好域，组织名为空就换成另一个域，现有设置读不到；
  - **数据目录**：`AppDataLocation` 是否随组织名变化，取决于 Qt 在各平台的路径规则。本计划不对它的目录层级做任何假设，只要求它与重构前一致，最终以真机上「原有数据都在」为准。
- 两个入口都直接调用这同一个函数，不另写身份规则。
- 打开数据库失败时，入口直接显示启动失败窗口：它只需要数据目录（取自 `DatabaseManager::defaultDatabasePath()`），
  不依赖 `SharedApp` 的后续阶段、`AppServices` 或 `QmlFacade::install`。offscreen 平台下照现状不进事件循环，直接返回 -1。

## 现状（写计划时核对，`main` `240534f`）

执行者开工时先核对这一节；有出入就停下报告。

- **平台分支**：服务层唯一的平台分支是 `PhaseSoundService.cpp` 的 `Q_OS_MACOS`（`AGENTS.md` 记录的现存例外）。
- **协调器**：`PendingDeletion`、`FocusSessionController`、`TaskInteractionCoordinator`、`PhaseCompletionNotifier`、`PhaseAlarmCoordinator`、`TrayController` 这几个类，
  没有被任何业务服务 include。唯一的例外是它们之间的 `FocusSessionController` → `PendingDeletion`。
  使用方是 `main.cpp`、iOS 桥接、`mcp/bridge`、`MacStatusBarController` 和测试。
- **Qt 模块**：`src/services`、`src/models` 用到 Core、Gui、Sql、Concurrent。
  - Gui 来自 `BackupService` 的 `QDesktopServices` 和 `ApplicationActivity` 的 `QGuiApplication`；
  - Network 只有 `SingleInstanceGuard`（Mac 专属）用到；
  - Quick 只有 `models/PlainTextLayout` 用到（`QQuickTextDocument`）。
- **同步**：
  - 同步引擎（`SyncEngine`、`SyncStore`、`SyncWorker`、`SyncFiles`、`SyncRecord`）对业务服务只有一处依赖，就是 `SyncEngine` 构造函数里写死的默认通知器 `SyncNotifier::publish`。
  - `SyncController`、`SyncedSettings` 依赖 `AppSettings`、`ScheduleService`，它们本来就是同步与业务之间的接缝。
  - `TrashService` 直接调用 `SyncNotifier::publishTableChanges`，在恢复之后复用同一套刷新。`SyncNotifier` 则经 `TrashNotifier` 转发，避免反过来依赖 `TrashService`。
  - 测试里直接构造 `SyncEngine` 的 9 处都已显式调用 `setChangeNotifier`，不依赖默认值。所以这些测试通过，**证明不了**生产路径完成了注入。
  - 生产路径上，引擎只在 `SyncController::ensureEngine()` 里创建。`ensureEngine()` 由 `startEngine()` 调用，后者有 4 个调用点：
    `initialize()`、`setEnabled()`、`acceptFolder()`、`finishRestore()`。引擎只在 `SyncController` 析构时销毁，没有中途销毁再重建的路径。
    同一个引擎可能在启动时就创建（上次开着同步），也可能在启动之后才创建（之后才开启同步，或之后才选定文件夹）。
- **应用身份**：`McpPaths::applyApplicationIdentity()` 把组织名、应用名都设成 `PomodoroTodo`；`McpProtocolTests` 已经断言这两个值。
  现在 `main.cpp` 在偏好域清理、单实例守卫和打开数据库之前调用它。
- **测试**：
  - 没有测试替身重定义产品符号，没有影响服务编译的测试专用宏，所以测试可以直接改链静态库；
  - 没有静态注册（`Q_COREAPP_STARTUP_FUNCTION`、`qmlRegister*`、`Q_IMPORT_PLUGIN`），代码放进静态库不会丢初始化；
  - `.qrc` 资源都在 `APP_SOURCES` 里；
  - PTCore 所需、但未列入 `APP_SOURCES` 的头文件有四个：`models/Task.h`、`models/CountdownGoal.h`、`models/FocusSession.h`、`services/ServiceReadResult.h`。
    `Task.h`、`ServiceReadResult.h` 虽然登记在其它测试目标里，也不代表它们已属于 PTCore；建库时四个都要补入。
    `services/SingleInstanceGuard.h/.cpp` 在 Mac 专属追加清单里，本来就不进入 PTCore。
  - 六个桥接测试通过复制其它目标的 `SOURCES` 复用业务源码，`McpSdkHost` 也采用同一机制。复制源清单不会继承链接库，改链时必须逐个显式链接 PTCore，完整名单见 057-A 第 5 步。
- **剪贴板**：`SyncController::copyRequested` 到 `QGuiApplication::clipboard()->setText()` 的连接在平台条件之外，Mac 与 iOS 共用；
  `McpAccessController::copyRequested` 的连接才是 Mac 专属。iPad 原生适配器另有 `UIPasteboard` 处理，本计划保持现状，不合并或删除它。
- **退出顺序**：整个仓库只有 `main.cpp` 连接了 `aboutToQuit`，按连接先后依次执行：
  1. Mac 外部 AI 接入 `shutdown`；
  2. 保存界面草稿；
  3. 提交待删项；
  4. 计时落盘；
  5. 备份收尾；
  6. 同步写出（最多 3 秒）；
  7. 关库。
- **iOS 前后台**：计时和同步对「前台」的定义不同，这是现有代码刻意保留的差别，抽取时不能合成一个 `isForeground`。
  - 计时（`GuiApplicationActivity`）：只有 `Active` 算前台。它在构造时先连上 `applicationStateChanged`，
    从前台变成任何非 `Active` 状态时发一次 `leftForeground`，计时器据此写检查点；`Inactive` 再到 `Suspended` 不会再发第二次。回到 `Active` 时记下时刻，供离线结算判断。
  - 同步（`SyncController::setApplicationState`）：`Inactive` 仍算前台（避免下拉控制中心、切换窗口就单独写一批文件）；只有 `Suspended`、`Hidden` 转入后台。
  - `main.cpp` 的处理在 `GuiApplicationActivity` 之后连接。每次状态变化：非 `Active` 时先保存草稿；然后**不论什么状态**都调用 `setApplicationState(state)`。
    所以回到 `Active` 时会调用 `setApplicationState(Active)`，让同步恢复前台节奏。

## 依赖门禁 `ArchitectureGate`

- **实现**：`tests/architecture_gate.py`，挂进 ctest（只在 Mac 构建注册，同其它 Python 门禁）。
  它读取 CMake 用 `file(GENERATE)` 写出的清单 `architecture-manifest.json`，内容是每个库的 `SOURCES`、`LINK_LIBRARIES` 与 `INTERFACE_LINK_LIBRARIES`。
  链接检查同时覆盖直接依赖和传给使用方的接口依赖：先解包静态库接口中合法的 `$<LINK_ONLY:...>`，再对两个链接属性的并集判断。
  不能把未知的生成器表达式当作空项跳过；无法解析时报告目标、属性与原始表达式，并判门禁失败，避免漏检。
- **为什么按源文件清单查，而不是按目录查**：文件不搬目录时，同在 `src/services/`、`src/models/` 下的两个文件，用相对路径互相 include 照样能编译；
  几个静态库最后都链进同一个可执行文件，Apple 的链接器也不报错。所以越层 include 只能按每个库的源文件清单来查。
  另外，测试目标改链静态库以后，就没有「只编最少源文件」带来的那层隐式检查了，这个门禁顺带补上。
- **规则**（随阶段增加）：

| 规则 | 加入阶段 |
| --- | --- |
| R1：PTCore 的直接与接口链接依赖只许 Qt6::Core、Gui、Sql、Concurrent | 057-A |
| R2：PTCore 的源文件 include 的项目文件必须属于 PTCore（解析顺序：所在目录 → `src/` → 仓库根） | 057-A |
| R3：PTCore 不 include `QQml*`、`QQuick*`、`QJS*`、`QtQml/…`、`QtQuick/…` | 057-A |

| 风险 | 应对 |
| --- | --- |
