## 方案

### R01 备份偏好预算

- 预算放在 `BackupOperations.h` 一处：条目数上限从 500 提到 40000（每日目标历史每天最多一个键，约 365 个/年，够用约 100 年），单值 64 KiB 不变，新增总字节上限 8 MiB（键与值的字节合计），限制外部文件的内存占用。
- 捕获、发布门禁、`inspectBackup`、`readEmbeddedSettings`、Mac 执行器协议都用这一份预算，删掉协议里写死的 500 和 64 KiB。
- 捕获后先查预算，超限直接失败，不生成快照；发布前除 `inspectBackup` 外再做一遍完整偏好读取，保证发布出去的文件恢复时读得出偏好。`inspectBackup` 也要拒绝偏好超限或编码不合法的文件。
- 不截断日期目标历史。备份失败不记成功时间、不清理旧备份。
- 兼容：旧版本遇到超过 500 条的新备份仍然拒绝，和现在一样；文件格式不变。

### R02 同步文件必需数组

`SyncJson::fromJson` 要求 `records`、`settings` 两个字段都存在且是数组，否则判为损坏（Corrupt）。合法的空数组照常接受；单条记录缺少旧版本没有的字段，仍按原规则兼容。从第一版写出代码（`f2bedea`）起，两个数组都会写出。

### R03 写回失败不清标记

`SyncNotifier::publish` 改用 `currentValues(&ok)`；读取失败时，今日目标的移除标记一律保留。只有 `SyncedSettings::remove` 返回成功、读取成功、键也确实不在了，才清标记。固定几项照原规则直接清。

### R04 同纪元坏快照补发

接收端读到坏快照时，请求序号就是坏快照覆盖到的序号 N，不再写 N+1。发送端在同纪元分支里，对请求序号等于当前快照覆盖序号（并且不超过已写出序号）的请求重写快照，按已有的请求指纹（`m_servedSnapshotRequests`）去重：同一请求只服务一次。正常补缺号的规则不变。

边界：升级前已经存下的 N+1 请求，要等发送端写出下一批才会被服务（旧行为）。在汇报里写明，不另做迁移。

### R05 请求存住才越过坏批次

`requestSnapshot` 先持久化，成功后才更新内存表和 `m_cursorDirty`，并把结果返回给调用方。坏增量的分支里，请求没存住就停在这一批：不推进游标，报错，下一轮重试。`afterScan` 里其他调用 `requestSnapshot` 的地方，也按同一原则检查返回值。

### R06 iPad 恢复清旧库上下文

`FocusStore.prepareForRestore()` 对齐 Mac 端 `onRestoreStarted`：取消自动衔接、清完成态、清待启动选择和切换确认。原生根用一个专用的 `BackupBridgeAdapter` 接 `onRestoreStarted`；自动衔接到点执行时，再经注入的 `operationBlocksInput` 读一次服务的阻断状态。待删槽在确认恢复时已经提交，不另处理。

### R07 阻断状态独立读取

`PTShellBridge` 增加一个不会失败的阻断状态读取（直接读 `BackupService` 内存状态）。`ShellStore.refresh()` 先读阻断状态，再读可能失败的摘要；摘要失败只保留旧数据并报错。阻断字段只有这一个来源。

### R08 仪表盘与搜索投影待删槽

`DashboardStore`、`SearchStore` 注入根上的 `PendingDeletionStore`，按任务 ID 过滤后再取前 6 条或发布结果，顺序以服务为准。统计数字仍按服务口径。

### R09 提示音切换重新预约

协调器监听 `soundEnabledChanged`，标记内容已变；同一运行段对账时先撤销、再新开一代预约，到点时刻不变。只处理提示音；休息时长等影响文案的设置记为遗留。

### R10 提交时才定秒数

协调器的预约操作在真正交给系统时才读计时器剩余秒数；被取代的、已过期的不提交，也不报「提醒不可用」。Apple 后端用 `SystemMonotonicClock` 扣掉权限查询的等待，扣完不大于 0 就不预约。

### R11 MCP 改期失败不广播

`TaskManager` 增加不发 `operationFailed` 的改期入口，只给 MCP 用；QML 和 iPad 桥接继续用原入口。不改 QML。

### R12 README

把「Qt 6.7 或更高」改成 Mac 构建的精确 SDK 要求，加上代码最低版本，两者都以 CMake 为准。
