## 背景

总计划「业务规则下沉」后面的「口径脚本」一段：

> 逻辑日（C++ 已有 `LogicalDay`）、学期周次（`ScheduleWeeks.js`）、投入档位（`HeatmapBands.js`）、例行星期（C++ 已有 `RoutineRules`）移到 C++ 或用 C++ 已有实现；纯显示格式（`Duration.js`、各页的 `Format.js`）在 Swift 重写，同一张输入输出对照表分别在 QML 测试和 `swift test` 里跑。

这一步要让 iPad 需要的所有计算口径都能从 C++ 拿到，或者有对照表可以对齐。这样 P4 写 Swift 时不用再自己发明一份。

### 现状（脚本与用到它的文件）

| 脚本 | 内容 | 用到它的文件 |
| --- | --- | --- |
| `qml/ScheduleWeeks.js` | 周次换算：`mondayOf`、`parseSemesterStart`、`weekIndexForDate`、`mondayOfWeek`、`dateOfWeekday`、`overlaps`<br>排版分簇：`layoutEntries` 一族<br>格式：`formatMinutes`、`parseMinutes`、`parityLabel`、`weekRangeLabel` | `components/Schedule{SettingsDialog,EntryDialog,Grid,EntryBlock}.qml`、`views/SchedulePlanView.qml`、`views/TrashFormat.js`（只用格式函数） |

| `qml/Duration.js`、`qml/views/{Dashboard,Memo,MonthGoal,Statistics,Trash}Format.js` | 纯显示格式 | 各自页面 |

## 范围

**做：**

1. **周次换算下沉**：新建 `src/services/ScheduleWeeks.{h,cpp}`。
   - 写成纯函数，命名空间写法照 `LogicalDay.h`，学期起始日作为参数传入，不依赖 `AppSettings`。
   - 在 `ScheduleService` 上加 `Q_INVOKABLE` 包装，供 QML 与将来的桥接层调用。
   - 课表相关 QML 改为调用 C++。
   - `ScheduleWeeks.js` 删掉换算函数，只留排版分簇和格式函数；`TrashFormat.js` 用到的格式函数原样保留。
   - `ScheduleService.h` 第 18 行那句「换算在 QML 侧完成」的注释照实改写。
2. **投入取档下沉**：新建 `src/services/HeatmapBands.{h,cpp}`（纯函数），在 `FocusHistoryService` 上加 `Q_INVOKABLE` 包装。
   - `MonthGoalView.qml` 改为调用 C++。
   - `HeatmapBands.js` 删除；还有别处在用的话，留成薄转发，并写明原因。
   - `Theme.qml` 注释照实改写。
3. **对照表**：新建 `tests/fixtures/calibers/`，每个口径一份 JSON。
   - Swift 侧已经有读取器：P3A 的 `src/ui/ipad/Tests/IPadCoreTests/FixtureReader.swift`，优先读这个目录。示例表 `Fixtures/display-clock.json` 的形状是 `[{"input": …, "expected": …, "reason": "…"}]`。
   - 表的结构沿用这个形状。多参数输入用对象，例如 `"input": {"date": "2026-02-28", "dayStartHour": 4}`。
   - 确实要换形状的话，同一个提交里改 `FixtureReader` 和 P3A 的示例测试，保持 `swift test` 全过。
   - 每条写输入、期望输出，再加一句为什么挑这组输入（边界、日界前后、闰年、学期跨年等）。
   - **C++ 侧**：周次、取档、逻辑日（`LogicalDay`）、例行星期（`RoutineRules`）各写一个测试，读表逐条断言。
   - **QML 侧**：还留在 JS 的 `LogicalDay.js`、`RoutineWeekdays.js`、`ScheduleWeeks.js` 的排版分簇与格式函数、`Duration.js` 与五个 `Format.js`，读同一组表逐条断言。
   - 这样，同一口径若有两份实现（C++ 与 JS），就被同一张表钉在一起；将来的 Swift 实现也读这张表。
   - QML 怎么读文件，由你选一个最小的办法。例如给这几个测试条目设 `QML_XHR_ALLOW_FILE_READ=1`，用 XMLHttpRequest 读，CMake 里照现有的 ENVIRONMENT 写法设；或者用现有测试宿主注入一个读文件的小对象。在报告里说明为什么选它。
4. **文档**：`docs/业务规则.md` 两节，加上「界面与验证约定」里一条新约定：同一口径有两份实现时必须共用对照表。

**不做：**

- 不改 19 个使用 `LogicalDay.js` 的 QML 文件，不改两个使用 `RoutineWeekdays.js` 的弹窗。这些 JS 留着，靠对照表与 C++ 对齐。
- 不改 `FocusView.qml`、`MainWindow.qml`，它们归 P2A。
- 不改显示文案和外观。
- `parseMinutes`（课表时间的文字输入）iPad 用系统时间选择器，不需要；留在 JS，不做对照表也行，做了更好。

## 步骤（每步一个提交）

1. **对照表格式与周次下沉**：
   - 定 JSON 结构；
   - 先从现有 JS 实现与现有测试里取一组覆盖边界的输入，生成表，人工核对每条期望值符合 `docs/业务规则.md`，**不要只是把现有实现的输出照抄成期望**；
   - 写 C++ `ScheduleWeeks` 与测试，ScheduleService 加包装；
   - 课表 QML 改为调用 C++，`ScheduleWeeks.js` 去掉换算函数；
   - 相关 QML 测试改为测接线。
2. **取档下沉**：`HeatmapBands` 写成 C++ 加读表测试，`MonthGoalView` 改为调用 C++，`tst_heatmap_bands` / `tst_month_heatmap_bar` 相应调整。
3. **两份实现的对照**：`LogicalDay`（含日界前后、跨年、夏令时不适用的说明）和 `RoutineWeekdays` 的表；C++ 与 QML 两侧都读同一张表。
4. **显示格式的表**：`Duration.js`、五个 `Format.js`、`ScheduleWeeks.js` 留下的格式与分簇函数各一张表，QML 读表断言。挑输入时覆盖：0、负数与 NaN、超大值、四舍五入边界、中文复数与量词。
5. **文档与收尾**：两节规则写明口径实现在哪；「界面与验证约定」加「同一口径两份实现共用对照表」；全量验证。

## 验收

- `~/pt-055-P2B` 全量构建零新增告警，全量 ctest 全过。
- 变异验证，每步至少两条，例如：
  - 周次换算的边界改一天 → C++ 与 QML 两侧的读表测试都失败；
  - 取档阈值从「小于」改成「小于等于」→ 失败；
  - 在 `LogicalDay.js` 里改一处日界判断 → QML 读表测试失败，C++ 不受影响，说明两份实现被钉住了。
- 报告里列出每张表的条目数，以及每张表被哪些测试读取。
- 外观不变：课表与专注历史页的离屏截图前后一致（照 project-pitfalls.md「离屏截图走查」，各截默认尺寸一张即可），截图放仓库外的临时目录，报告里写结论，不入库。
