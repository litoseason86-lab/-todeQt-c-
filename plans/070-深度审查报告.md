## R01：备份发布与恢复的偏好预算不一致

**位置：** `src/services/AppSettings.cpp:951`、`src/services/BackupOperations.cpp:81`、`:996`、`:1250`，`src/services/BackupExecutorProtocol.cpp:133`。

每日目标按日期新增 `focus/dailyGoalHistory/<date>` 并长期保留。捕获偏好时读取全部自有键；创建快照的发布门禁只执行 `inspectBackup`，没有执行 `readEmbeddedSettings` 的完整偏好校验。后者恢复时才拒绝超过 500 项的偏好。

隔离探针通过真实 `AppSettings::setDailyFocusGoal` 逐日增加历史，在 **500 / 501 个自有键**两侧调用当前实现，结果为：

| 自有键数 | 创建快照 | `inspectBackup.valid` | 读取恢复偏好 | Mac 执行器协议 |
| --- | --- | --- | --- | --- |
| 500 | 成功 | true | 成功 | 接受 |
| 501 | 成功 | true | 失败：备份偏好条目过多 | 拒绝：偏好条数超限 |

**平台边界：** Mac 正常异步路径在隔离执行器协议处安全拒绝，不能声称该路径继续发布。iOS 进程内异步路径，以及同步 `createBackup`、`runAutoBackupIfDue`、`backupBeforeSyncReplace` 路径可以发布上述文件。`BackupService.cpp:724`、`:1148` 的成功路径仍记录备份时间并清理保留数量，因此 iOS 自动备份可能逐渐挤掉旧的可用恢复点；同步替换前的安全备份也存在同一可恢复性缺口。

**修正方向：** 发布、检查、恢复和 Mac 协议共用完整偏好预算契约，同时支持正常日期历史增长。禁止通过截断日期目标历史掩盖超限。

**补测：** 500/501 边界和长期日期历史的创建—检查—恢复往返；分别覆盖两类执行器。失败的新备份不得推进成功时间或触发保留清理。当前探针执行到恢复必经的偏好读取门禁，没有冒充完整恢复服务或真机往返。

## R02：缺失数组被当成合法空快照

**位置：** `src/services/SyncRecord.cpp:160`、`:191`，`src/services/SyncFiles.cpp:356`，`src/services/SyncStore.cpp:558`，`src/services/SyncApplier.cpp:1156`。

`records` 和 `settings` 直接调用 `toArray()`，缺失或错类型都得到空数组，函数仍返回成功。外层文件格式、设备和纪元正确时，`decodeSnapshot` 没有再拒绝这一结构。

真实解析器探针针对可读格式 1–4，各运行一个合法对照和四个异常结构：`records` 缺失、`records` 为对象、`settings` 缺失、`settings` 为对象。**4 个对照及 16 个异常结构全部返回 Ok**；缺失的集合变为 0 项。探针只处理内存中的虚构数据，未执行数据库替换。

首次加入或采用高纪元时，整体替换会调用 `dropRecordsMissingFrom`。空记录集合使本地可发布、带同步身份的记录被视为快照中不存在，随后删除；进行中的专注与预置科目有明确保留分支。空设置集合会清同步设置，并为原逐日目标登记移除。替换前会创建安全备份，因此不应描述成没有恢复机会。

格式 1、2 的历史写出实现已经包含这两个数组；后续格式扩展同步表。每条记录缺少旧版本尚不存在的字段是另一条明确兼容规则，不能一并收紧。

**修正方向：** 转换前检查两个集合字段存在且类型确为数组；错误应成为 Corrupt。保留合法空数组和旧记录缺列兼容。

**补测：** 可读格式分别覆盖缺失、null、对象、字符串及合法空数组；高纪元坏结构不得进入替换或推进纪元。

## R03：写回失败后误清移除标记

**位置：** `src/services/SyncNotifier.cpp:47`、`:56`、`:64`，`src/services/SyncedSettings.cpp:74`，`src/services/SyncController.cpp:2005`。

整体替换移除某日目标时，`SyncNotifier` 忽略 `SyncedSettings::remove` 的返回值，随后调用 `currentValues()` 又不取成功标志。偏好后端不健康或节次读取失败会使该接口返回空映射；`!now.contains(key)` 随即被当成删除已经完成，并清掉数据库中的 remove 标记。

隔离探针用专用临时 INI 的权限故障，直接运行真实 `SyncNotifier::publish`，得到：

```json
{"marker_before":true,"marker_after":false,"settings_read_succeeded_during_fault":false,"old_goal_after_recovery":120}
```

故障解除后旧目标仍在，待写回标记已经消失。启动核对的现有代码会将没有待写回标记的本地残留目标作为本机新值记入同步。后一步为源码链推导；本轮未将跨进程重新发布写成已实测。

`reconcileSettings` 已经检查读取健康状态并保留失败标记；缺口位于普通同步通知的另一条出口。

**修正方向：** 使用 `currentValues(&ok)`，读取失败时保留标记；单项移除失败也不得确认完成。

**补测：** 移除目标时持续偏好写失败，恢复健康并重启后旧目标不得复活或重新入队。

## R04：同纪元坏快照的补发条件无法满足

**位置：** `src/services/SyncEngine.cpp:646`、`:655`、`:915`、`:933`，`src/services/SyncWorker.cpp:393`。

发送端已经压缩到第 N 批，`covered=written=N`，没有新改动；落后接收端需要该快照，但收到的副本损坏。接收端请求 N+1，发送端同纪元分支要求 `request.seq > covered && request.seq <= written`，因此不重写。没有新批次也不会触发数量压缩条件，定时重试不能自行打破等待。

高纪元分支已有在相同覆盖位置按请求指纹重写的机制。本项不同于已修复的高纪元坏快照，也不同于请求去重；原数据仍在发送端。

**修正方向：** 对同纪元损坏请求允许重写当前覆盖位置，使用请求指纹去重，不能用一个尚不存在的序号表达重写意图。

**补测：** 同纪元坏快照、无后续本地改动、多轮维护恢复；同一请求只服务一次。当前为源码条件链证明，未运行新的 FakeICloud 场景或真实 iCloud。

## R05：请求保存失败后仍越过坏批次

**位置：** `src/services/SyncEngine.cpp:631`、`:685`、`:851`，`src/services/SyncStore.cpp:1131`、`:1221`，`src/services/SyncWorker.cpp:379`。

同纪元 `requestSnapshot` 忽略请求保存失败，但处理坏增量时继续保存跳过游标。写 `cursor.json` 又从数据库重新读取请求，所以失败的请求没有发出。下轮从已推进的游标后读取；只有一批、没有后续缺号和新快照时，故障恢复或重启都不会重新请求该批。

内存 SQLite 前提实验仅拒绝 `request/%` 写入，游标写入照常成功，结果为 `request_write_failed=true`、`cursor=0:1`、`request_count=0`。这证明两个独立写入可以产生该状态，不等于真实磁盘满必然产生相同结果，也不是完整引擎复现。

高纪元路径已有请求持久化失败回归；`corruptFileIsSkippedLoggedAndHealedBySnapshot` 覆盖的是请求正常保存后的恢复。后续新快照、新纪元或人工重建仍可能恢复内容，后果应表述为持续分叉。

**修正方向：** 请求保存成功后才允许越过坏批次；考虑将日志、请求和跳过游标作为同一记账事务提交。

**补测：** 同纪元请求写入失败、游标可写；故障解除后必须补回内容。

## R06：iPad 恢复未清旧库任务身份与待续动作

**位置：** `src/ui/ipad/Sources/IPadUI/Bridges/BackupBridgeAdapter.swift:20`，`src/ui/ipad/Sources/IPadCore/Stores/SettingsBackupStore.swift:24`，`src/ui/ipad/Sources/IPadCore/Stores/FocusStore.swift:368`、`:405`、`:584`，`src/ui/ipad/Sources/IPadUI/NativeRoot.swift:55`。

桥接已转发 `onRestoreStarted`，原生装配没有消费。旧库待机选择 id=7，恢复库中另一条任务也 id=7 时，`reconcileSelectedTask` 会保留编号并改成新任务标题，旧选择意图自动接到了另一个身份。`docs/业务规则.md:444` 明确要求换库前清空上下文，Mac `MainWindow.qml:1510` 已处理。

同一缺口还保留阶段结束后的 0.9 秒自动衔接回调；执行点没有恢复阻断守卫。服务只在恢复准入时拒绝已有计时，不能阻断准入后的延迟启动。这个竞争窗口尚未动态复现，不据此声称已发生数据库损坏。

**修正方向：** 原生根独立订阅恢复开始，清待机选择、切换确认和待续动作，取消自动衔接；延迟回调执行时再检查恢复状态。恢复后合法的计时事实仍由服务恢复。

**补测：** 两库同号不同身份；已排队衔接之后开始恢复，回调不得再启动计时。

## R07：恢复控制状态与摘要读取耦合

**位置：** `src/platform/ios/bridge/PTShellBridge.mm:145`、`:175`，`src/ui/ipad/Sources/IPadUI/Shell/ShellBridgeAdapter.swift:23`、`:39`，`src/ui/ipad/Sources/IPadCore/ShellStore.swift:225`，`src/ui/ipad/Sources/IPadUI/Shell/ShellRootView.swift:131`。

Shell 桥接将数据库未开、摘要或缺口查询失败标为整份快照无效。Swift 适配器在复制恢复阻断值之前抛错，ShellStore 只更新错误，保留旧 `operationBlocksUI`。

因此读取故障与进入恢复交叉时可能继续缓存 false；反向在恢复失败且数据库无法重开时，服务已解除 busy，Shell 却可能继续缓存 true，遮罩遮住失败结果。`BackupService::setBusy` 本身会先提交完整状态再发通知；问题发生在展示侧读取契约。轻量计时刷新不更新阻断字段。

**修正方向：** 将恢复控制状态独立于可失败的业务摘要投影；摘要失败保留旧数据和错误，控制状态仍接收当前值。

**补测：** 在桥接与 Swift 两层交叉覆盖摘要失败时进入、退出阻断。当前为静态状态链证明，未在设备制造恢复故障。

## R08：iPad 待删任务仍出现在仪表盘与全局搜索

**位置：** `src/ui/ipad/Sources/IPadCore/Stores/DashboardStore.swift:13`、`:39`，`src/ui/ipad/Sources/IPadCore/Stores/SearchStore.swift:38`，`src/services/PendingDeletion.cpp:46`。

待删服务只登记编号、开撤销计时并发 changed，不立即删数据库行，也不发 tasksChanged。仪表盘直接取原始任务前六条，没有观察或过滤待删状态；全局搜索同样发布原始结果。因此已经提示已删除的任务仍能显示和操作。VoiceOver 会暂停自动提交，不能只视作几秒视觉残留。

今日任务、本周计划和今日工具搜索已消费共享待删槽，证明持久化延迟本身是有意设计。

**修正方向：** 注入同一待删状态并按稳定 ID 投影；仪表盘先过滤再取六条，保持服务顺序并让第七条补位。需要摘要预览时继续由服务提供口径。

**补测：** 仅发 pending.changed 时立即隐藏；撤销及提交失败恢复；第七条补位顺序保持。当前为装配与状态链证明，未做 iPad 视觉验收。

## R09：提示音切换未更新系统预约

**位置：** `src/services/PhaseAlarmCoordinator.cpp:19`、`:98`、`:135`，`src/platform/apple/AppleNotificationBackend.mm:261`，`src/ui/ipad/Sources/IPadUI/Pages/Settings/SettingsPage.swift:92`。

iOS 开始番茄时将提示音设置写入系统预约。计时中关闭或打开提示音后，协调器不监听对应设置变化，同运行段也直接复用旧预约，系统仍按初始声音配置投递。完成时读取当前设置的即时通知会因预约覆盖被抑制，无法纠正已预约内容。

**修正方向：** 配置变化使当前预约失效，保留原到点期限重新预约；保留串行取消及代次检查，防止重复提醒。

**补测：** 有声到静音、静音到有声、预约尚未完成时切换。现有假后端丢弃 playSound，需先保存它才能断言。系统声音结果须另做设备验证。

## R10：排队耗时被叠加到预约期限

**位置：** `src/services/PhaseAlarmCoordinator.cpp:119`、`:168`，`src/platform/apple/AppleNotificationBackend.mm:243`、`:249`，`src/services/NotificationService.cpp:133`。

协调器入队时记录剩余相对秒数，等待串行撤销完成后仍提交原值；后端又等待权限查询返回后才创建相对触发器。等待 D 秒会把提醒向后移 D 秒；若等待期间阶段已经结束，旧 Schedule 仍可能创建未来提醒。显著延迟以系统异步操作实际发生等待为条件，不声称正常设备固定延迟多少秒。

**修正方向：** 保留原到点期限，在实际提交前扣除等待时间；过期操作不得得到新的未来触发时间。时间基准应与计时器一致。

**补测：** 假时钟与延迟后端验证入队后剩余时间递减及排队期间过期；权限查询延迟另行注入验证。当前未运行真实平台延迟测量。

## R11：MCP 改期失败污染加载错误（P3）

**位置：** `src/mcp/bridge/McpTaskWrites.cpp:141`，`src/services/TaskManager.cpp:1499`，`qml/views/TodayTaskView.qml:242`、`qml/views/WeekPlanView.qml:105`、`qml/views/DashboardView.qml:181`。

MCP 合法改期读取成功、UPDATE 被拒绝时，服务发出共享的任务改期失败信号。三个活动页面没有过滤或认领该写入来源，将其写入页面 loadError；失败又不发 tasksChanged，错误不会由成功刷新自动清除。读工具、新建、完成和普通修改的已有隔离不覆盖这条路径。

**修正方向：** 外部写入使用能返回具体失败且不广播页面加载错误的结果入口，或精确认领本页面发起的改期失败。不能全局屏蔽成功刷新信号。

**补测：** MCP UPDATE 拒绝时任务不变、返回失败且页面 loadError 不变；本页面主动拖放仍显示失败。影响限于反馈归属，本轮按 P3 处理。

## R12：Qt 构建文档版本不准确（P3）

**位置：** `README.md:110`，`CMakeLists.txt:43`，`cmake/QtSqliteRuntime.cmake:3`。

README 声称 Qt 6.7 或更高 SDK 可用，Mac 专用 SQLite 驱动配置对非 6.10.3 版本直接拒绝。按入口文档选择其它版本会在配置阶段失败。

**修正方向：** 写明 Mac 当前精确 SDK 限制，并区分通用代码最低 API 版本。静态核对足够，无需为文档再构建。
