# 当前业务规则

本文记录当前实现必须保持的业务边界与跨层约定。功能总览见 [README](../README.md)，构建和测试见 [运行命令](运行命令.md)，待办与未采纳决策见 [计划索引](../plans/README.md)。

## 专注、日期与任务

- 专注规则统一定义在 `src/services/FocusSessionRules.h`：单段有效门槛为 3 分钟；`validPomodoroCountExpr` 只计番茄模式自然到点的有效记录，`focusedSecondsExpr` 累计两种模式的有效时长。自由计时不折算番茄数。
- 任务预计用时、今日专注目标、长期目标以分钟计量；输入共用 `DurationFieldPair.qml`，格式化共用 `qml/Duration.js`。任务实际投入从专注记录派生，达到预计用时可自动完成任务。
- 专注与任务归属使用逻辑日，默认从凌晨 4 点开始。日期计算统一走 `LogicalDay`；QML 必须在日界变化时更新可观察的日期状态，不能依赖 `new Date()` 自动触发绑定重算。课表使用自然星期，不套用专注记账日期。
- 今日任务按完成状态、当天 `display_order`、创建时间、编号稳定排序。新建、结转和改期任务追加到目标日末尾；重排必须提交当天完整任务集合，不能重复或漏项。拖动期间保持模型稳定，松手后再写入顺序。
- 每日例行生成必须幂等，不重复生成，不补齐所有历史日期；当天删除过的实例不能因刷新而复活。
- 任务列表的“开始”按上次使用的模式直接启动；同任务同模式重复点击只回到当前计时。切换活动任务或模式先确认，保存失败不启动下一段；超长自由专注仍需核对时长。
- 任务编辑支持 2000–2100 年的任意有效日期；日期输入回查年月日，拒绝 JavaScript 自动进位产生的伪日期。批量改期在一个事务内校验全部编号，失败整批回滚；已在目标日期的任务保持排序。
- 搜索覆盖全部日期的标题、备注和科目，可筛选完成状态；结果分批加载，最多显示 10000 条并提示缩小范围。搜索或筛选变化会清空批量选择，待撤销删除的任务不出现在结果中；任务本身变化时保留勾选，只丢掉已不在结果里的编号。
- 批量改期的「选择逾期」沿用逾期口径，排除例行生成的实例——它们不参与结转，搬到今天会和当天新生成的实例重复。
- 复制任务只复制标题、科目、预计用时和备注，不复制完成状态、计时记录或例行生成标记。连续录入保留日期、科目、预计用时，成功后清空本条内容，失败保留草稿。
- 手动补录记为自由计时。新增和修改都拒绝未来时间、重叠区间、低于有效门槛的记录；不能修改正在进行的会话。
- 补录与修改的任务候选按与所选日期的距离排序并限量；被编辑记录的原归属任务始终出现在候选中，否则保存会把它静默改成未关联。

- 专注与休息记录均支持撤销删除和纠正类型；专注记录还可修改任务归属；休息转专注不能伪造已完成番茄。只提交实际改动的字段，不改时间时保留原始秒数、毫秒和暂停跨度。
- 专注与休息记录共同参与区间冲突校验，包含正在进行的计时；两个表的编号独立，编辑和删除必须同时携带记录类型。历史变化由装配层通知任务和目标刷新。
- 休息（含进行中的休息）按「起点 + 实际计时」占用时间线，不按区间两端：暂停和关机时段并没有在休息，按区间算会让一次忘记结束的休息挡住整段时间的补录。
- 只改归属或类型、区间没有变化时不重跑重叠校验；否则历史遗留的重叠会让用户连纠正归属都做不到。休息转专注会把占用放大到整段区间，仍要重新校验。
- 删除暂缓提交并提供撤销。新的删除、替换提示、手动备份、恢复、退出，以及补录或修改记录之前，先提交待删除项：撤销窗口内记录仍在库里，不先落库就写入会撞上用户已经看不见的那条记录的时间段。

### 主动休息与超长自由专注

- 主动休息入口位于今日任务页，仅在计时器空闲时可开始。它与番茄休息是不同阶段，均不写 `focus_sessions`，不增加番茄数、今日专注或长期目标进度。
- 主动休息与番茄休息结束后写入独立的 `rest_sessions`，出现在今日专注时间轴，但不进入专注时长和次数统计。结束点按「起点 + 实际计时」写入，暂停与关机时段不算休息。
- 主动休息支持暂停、继续和结束；重启后只恢复为暂停状态，不把离线经过时间补入计时。结束后返回今日任务页。
- 自由专注超过提醒阈值时，结束前确认记录或丢弃，并可向下修正时长。未编辑时保留原始秒数；编辑后按整分钟处理，最少 3 分钟，不能超过实际计时时长。前端与服务层都校验。
- 修正记录的结束时间必须等于开始时间加修正时长，避免区间与时长矛盾，阻挡后续补录。保存失败时保留当前会话供重试。

## 长期目标与奖励

- 目标必须绑定有效科目；按科目和起始日期从专注记录派生投入分钟、进度、预测和月历热力，不冗余存储累计进度。课表与休息没有专注记录，因此不参与目标累计。
- 完成日期预测使用最近 14 个自然日（从目标起始日起截断）的实际投入，未学习日也计入分母；至少观察 7 日且有 2 个学习日才预测日期。按历史学习日平均投入估计的“还需学习日”单独展示，不能与截止自然日直接比较。
- 奖励通过全局信号送达，避免用户停留在专注页时看不到进度反馈。目标页承担列表、详情、100 格进度与热力展示。
- 25/50/75/100% 里程碑用 `fired_milestones` 位掩码记录哪些档位已触发。普通进度回退不清除奖励位，重新达到旧档位不重复庆祝；一次跨多档只通知最高档。
- 修改目标值、科目或起始日会改变进度定义，按新定义重新对齐奖励位；只改标题或截止日保留奖励位。目标字段与奖励状态在同一事务提交，避免半保存。
- `achieved_at` 记录首次达成时间，进度回退不抹除。新建目标会对齐已有历史进度，不能在下一次专注结束时把旧投入当成新里程碑补弹。
- 沉浸模式压制庆祝弹窗；`reduceMotion` 与 `soundEnabled` 控制动画和音效降级。统计页等级与已达成列表已按产品决定撤回，目标维度导出尚未实现，二者都不是当前交付承诺。

## 课表

- `schedule_entries` 与 `schedule_periods` 独立于任务和例行任务。课表按星期、时段、周次范围及单双周循环，没有完成状态，不生成任务，不接专注计时，不参与统计与目标进度。
- 服务层负责存储、给定周次的查询和冲突判断；`qml/ScheduleWeeks.js` 负责日期与学期周次换算，避免服务层依赖界面设置。
- 时间轴按真实时长排布，节次模式按等高节次排布，两者共用起止分钟数。冲突必须同时具备时间重叠和实际共同生效周；仅周次范围交叠还不够。
- 周次范围被单双周规则完全排除时拒绝保存。视觉泳道按显示区间分配，短块放大或映射到节次后也不能互相盖住；未落入节次或被周末开关隐藏的条目要明确提示。
- 课表设置先校验全部输入，再保存节次、批量同步学期设置；设置写入失败时补偿回滚旧节次，回滚失败单独报告。这是数据库与设置文件之间的补偿流程，不是跨文件原子事务。
- QSettings 写入失败必须恢复旧缓存及原先不存在的键，不能仅重建对象；成功落盘后才发成功变更信号，失败后允许重试。读取失败不能伪装为空列表。

## 知识缺口

- `knowledge_gaps` 与 `tasks` 的分界只有一条：任务必须有日期（`tasks.date` 是 `NOT NULL`），而知识缺口的常态是「现在还定不了什么时候处理」，所以 `due_date` 允许为空。这条差别是这个实体存在的全部理由，不能为了「统一」把它并回任务。
- 知识缺口不接专注计时，不写 `focus_sessions`、`rest_sessions`，不计番茄数、今日专注与长期目标进度，也不进统计页。要专注就先 `convertToTask` 生成任务，再从任务启动——专注口径只有 `FocusSessionRules` 一份。
- 捕获入口必须是非模态、不影响计时的 `Popup`，只收一行标题，不追问日期、优先级和科目。专注页那个入口带来源任务与其科目；今日任务页的入口没有「当前任务」概念，不带来源。捕获一旦需要停计时或多做一次决策，这个功能就等于不存在。
- `source_task_title` 是写入时的快照。外键为 `ON DELETE SET NULL`，任务删除后编号变空，但来源文字必须保留——它属于记录当时的现场，与 `focus_sessions` 存科目快照同理。
- `detail`（当时遇到了什么）与 `resolution`（后来想明白了什么）分列存储，不能合并。三个文本列都是 `NOT NULL`：空 `QString` 绑定会写成 SQL NULL，所有写入路径必须先收敛成空串。
- 状态由到期日派生：有 `due_date` 即「已安排」，没有即「待处理」；`resolveGap` 显式置「已解决」。编辑一条已解决的记录不重新打开它，重新打开必须是显式动作；`reopenGap` 清 `resolved_at`、保留 `resolution`；重复解决不覆盖首次 `resolved_at`。已解决的条目拒绝排期与转任务。
- 逾期不自动顺延。任务有结转，知识缺口没有：把 `due_date` 推到今天会抹掉「这条拖了多久」，而拖了多久正是判断该不该立刻停下来处理它的唯一依据。逾期条目保持原日期，界面显示已逾期天数。转任务同样不能把它清零：`convertToTask` 的到期日取原到期日与任务日期中较早的一个——已逾期的保持原日期，未排期的补成任务日期（状态由到期日派生），排在以后的提前到任务日期。
- 关联任务完成不自动解决缺口。做完任务完全可能还是没搞懂，服务只报 `linkedTaskCompleted` 这个事实，由用户决定是否标记已解决。
- 排序不变量：已解决沉到最后，其余按到期日从早到晚、未排期沉到已排期之后，再按优先级高到低与创建时间兜底。第一个排序项是 `(status = 2)` 而不是 `status ASC`——后者会把全部未排期条目顶到已排期前面。
- 「今天」「逾期」的判定一律走逻辑日，由 `getReminderSummary` 在服务层算好；QML 不自己比日期，并在日界或 `dayStartHour` 变化时重查。提醒摘要区分「读取失败」与「确实没有待办」，失败时提示条保持安静。`dueToday`、`overdue`、`oldestOverdueDays` 不计已有没做完关联任务的条目：它们已经作为任务出现在今日页，再催只会诱导重复转任务；关联任务做完而条目仍未解决时重新计入。
- `convertToTask` 在一个事务内完成查现状、建任务、置已安排、记 `linked_task_id`；任一步失败整体回滚，缺口状态原样不动。已有没做完的关联任务时拒绝再转，不建重复任务、不改写关联——按 JOIN 到的任务行判断，编号悬空视同没有关联；关联任务做完而条目仍未解决时允许再转。列表行的 `linkedTaskOpen` 与这条拒绝条件同一口径：清单页据此禁用「今天做」，今日页批量转任务据此跳过。`display_order` 取当天最大值 +1，与 `TaskManager::addTask` 一致。批量改期同样整批校验、整批回滚。
- 今日页「全部加到今天」的失败条目单独提示数量与原因（`knowledgeGapConvertError`），不能只报成功数量，也不能挂在 `loadError` 上：部分成功会触发任务列表刷新，刷新成功就清掉 `loadError`。提示条安静下来时一并清空。
- 知识缺口弹窗每次打开与收到 `categoriesChanged` 时重查科目；选中的科目已被删除就退回「不指定」，否则保存会撞外键。
- 事务内语句失败后必须先 `finish()` 再 `rollback()`。仍然打开的 statement 会让 SQLite 继续持有表锁，之后的迁移与备份 `VACUUM INTO` 会以「database table is locked」失败，而现场早已离开出错的地方。
- 删除采用二次确认，不接入撤销窗口。撤销窗口带着「备份、恢复、退出、补录之前必须先提交待删除项」这条硬约束，多接一个域就多一处会漏掉的 flush。
- 知识缺口是 schema v14 新增表，走 `user_version` 迁移链而不是 `rest_sessions` 那种「不升版本、每次幂等建表」的做法：后者在恢复不含该表的旧备份时会建出空表，把数据丢失伪装成恢复成功。备份校验只对 v14 及以后的备份要求这张表存在，更早的备份允许缺失，由恢复后的迁移补齐。表存在还不够：启动与备份共用 `DatabaseManager::knowledgeGapForeignKeysAreValid`，外键必须恰好是 `category_id`、`source_task_id`、`linked_task_id` 三条，删除动作一律 `SET NULL`。只校验列和 CHECK 会放过 `ON DELETE CASCADE` 的表——恢复与启动都正常，删掉一条任务却会连带删掉关联它的缺口。

## 侧栏顺序

- 侧栏条目顺序可由用户在「设置 → 外观 → 侧栏顺序」重排，存在 `appearance/sidebarOrder`（逗号分隔的视图 id）。`appearance` 已在 `AppSettings::ownedSettingGroups()` 中，备份与恢复自动覆盖。
- 存的只是顺序，不是条目集合。`AppSettings::defaultSidebarOrder()` 是「当前版本有哪些可排序页面」的唯一清单；`normalizeSidebarOrder` 在读写两端都跑：保留认识的 id 并维持用户顺序、丢掉已不存在的 id、去重，最后把清单里有而记录里没有的页面补到末尾。
- 新版本新增页面时必须补在末尾，不能因为旧记录里没有它就不显示——用户会以为这个版本没有这个功能，而且完全无从排查。同理，降级运行或手改配置留下的未知 id 一律丢弃而不是原样渲染。
- 新增一个页面要同时改 `AppSettings::defaultSidebarOrder()`、`Sidebar.qml` 的 `entryPresentation` 和设置页的 `sidebarEntryNames`。只改一处会让那一页缺文案或缺入口，`QmlTest.sidebar_order` 的 `test_everyDefaultEntryHasPresentation` 负责在漏改时转红。
- 「设置」不是视图，固定钉在侧栏底部，不进顺序列表。顺序既然由用户决定，原先「时间视图」分组标题与分隔线就不再成立，已一并移除。
- 切页快捷键绑定的是视图而不是侧栏位置，重排不改变 ⌘1–⌘8 的目标页。
- 设置页整份提交新顺序，不做相邻项就地交换：`sidebarOrder` 读出来的是副本，改副本不会回写，只会让界面与存储悄悄分家。
- 设置页用拖动排序，不提供 ↑ ↓ 按钮（2026-09-11 用户看过设计稿后选定：行更干净，接受键盘调不了顺序）。拖动期间完全不动模型——中途改模型会重建全部行，正在拖的那一行连同它的 `DragHandler` 一起被销毁；只记「谁在拖、落在第几位」，松手才整份提交。落点按指针所在行算，指针出界夹到首行或末行；拖到滚动区上下边缘自动滚动，滚动时用最后的指针位置重算落点。

## 专注页任务选择与「开始专注」的口径

- 「开始专注」在三处必须同口径：仪表盘按钮、专注页按钮、⌘↩ 与全局热键。取哪一条由
  `FocusView.autoStartCandidate()` 一处决定——已有有效 `selectedTaskId` 时优先用它
  （用户刚在今日页点过某条，按快捷键不该被换成别的任务），否则取 `getTodayTasks()` 里
  第一个未完成的（该查询已按未完成在前、当天 `display_order` 升序排好）。候选范围是**逻辑今日**，
  不是「全部未完成任务」。
- **已有选中项要先按编号回查仍然存在才用**（`selectedTaskStillExists()`）。选中项只在少数路径里清空，
  在今日页删掉任务不会清它；拿已删除的编号去启动，服务端 `INSERT … SELECT … WHERE t.id = :taskId`
  插入 0 行而失败。失效就清掉选中项、继续找今日候选，找不到才展开选择器。
- 「今天还没有可以开始的任务」这句提示**只在选择器确实展开时**出现（`shortcutOpenedSelector`）。
  取到了任务、只是启动失败时，失败原因由专注页的错误文字说明，不能被报成「没有任务」。
- 取不到可自动启动的任务时**展开选择器**，不按「今天有没有任务」分叉。
  「今日零任务」与「今日任务全部已完成」是两种不同的到达方式，按前者分叉会让后者
  掉进没有规则覆盖的空分支，表现为按了键什么都不发生。
- 选择器里已完成的任务排在末尾但**仍可选**——「今天排的都做完了，还想再练一轮」是常态。
  当前计时绑定的那条即使已完成、即使已不属于今天，也必须出现在候选里，否则从选择器
  走一圈回来会把归属静默改成别的任务（与补录候选「被编辑记录的原归属任务始终出现在候选中」同构）。
- 选择器**不提供「不关联任务」**：实时计时必须绑任务（`canStartFreeFocus` 要求 `selectedTaskId > 0`）。
  统计里的「未关联专注」来自补录与历史数据，不是实时路径。不要照搬 `ManualSessionDialog` 的
  `taskOptions`——它首项恒为「不关联任务」，候选来自历史服务并按所选日期就近排序，用途是补录。
- 选择器只在空闲时出现（没有进行中的会话、也不在主动休息里）。计时进行中任务由计时器说了算，
  换任务要走 `requestTaskSwitch` 的既有确认流程，标题退化为只读。
- 选择器里新建任务后要立刻启动它，因此必须拿到新任务的编号——走
  `TaskManager::createTask(...) -> int`（成功返回编号，失败返回 `-1`；四个 `addTask`
  重载都以它为实现）。**不允许按标题反查**：同一天允许同名任务，标题加 `display_order`
  不是唯一键，反查会把这段专注记到另一条任务上而用户看不出来；加一条「查不到就报错」
  也只防漏查、防不了误匹配。`createTask` 返回 `-1` 时不启动任何计时并报错。
  插入成功却读不出编号时照常发 `tasksChanged`（行确实写进去了），但仍返回 `-1`——
  **绝不返回一个猜来的编号**。
- 当前选中的任务被标记完成、或被改期离开今天，仍留在选择器候选里并保持选中
  （`FocusTaskPicker.candidates` 在今日列表里找不到它时补在最前）。
  专注页只在自己是当前页时响应 `tasksChanged`，切回本页时另有重读。

## 记一笔的键盘入口

- `gap.capture`（应用内）与 `global.captureGap`（全局）都落到
  `MainWindow.captureKnowledgeGapFromShortcut()`。它们是捕获动作不是切页动作，
  与 2026-09-03「切页快捷键只覆盖 8 页」那条决策无关。
- **窗口未激活时不能直接开捕获框**：此时键盘焦点还在原来那个应用里，框开出来用户打的字会落到别处。
  先把请求记在 `pendingGapCapture` 并发 `windowActivationRequested`，由 `main.qml` 完成
  show/raise/requestActivate；等 `windowActive` 真的变真，`onWindowActiveChanged` 才打开框。
  窗口操作留在窗口那一层，`MainWindow` 只表达意图。
- **挂起的请求必须可过期、可取消**：`gapCaptureRequestTimeoutMs`（默认 3 秒）内等不到激活就作废，
  `cancelPendingGapCapture()` 可随时取消。系统若拒绝把窗口提到前台，不作废的请求会在
  用户下一次随手打开应用时突然弹出捕获框，可能已经隔了一小时。
- 捕获被阻断的条件是 `gapCaptureBlocked()`：弹窗占着焦点（`overlayHoldsFocus`）、正在录快捷键，
  或备份/恢复正处在数据库临界区（`backupOperationBlocksInput`）。三项与 `AppShortcuts.suspended`
  同一口径，必须在这一处一起判：全局热键不经过 `suspended`；`triggerShortcutAction` 入口的
  数据库守卫只管分发那一刻，管不到激活时才执行的挂起请求。捕获框挂在 overlay 上，
  会盖过恢复遮罩并接收键盘。
  **挂起的请求在激活后、执行前要再判一次**——挂起期间可能开了弹窗、进入了录制或开始了恢复。
  被挡住的请求直接作废，不留到下一次激活，阻断结束后也不补弹。
- **已知潜在风险（未复现、未修复）**：快捷键分发里另有三条经 `Qt.callLater` 延后执行的路径——
  新建任务、开始/暂停专注、结束专注。`triggerShortcutAction` 入口的数据库守卫只管分发那一刻，
  延后那一步执行前没有再判 `backupOperationBlocksInput`。恢复阻断目前只由用户在弹窗里确认后同步置真
  （自动备份不阻断输入），要撞上需要确认点击恰好落在分发与延后执行之间。
  **时间窗口短不等于事件顺序有保证**，不能记为已证明不可达。
- 在专注页、且专注页自己的入口可用（`FocusView.knowledgeGapEntryAvailable`）时，
  走专注页那个入口（带来源任务与科目）；其它页面走窗口级的无来源捕获。
- **主动休息时走窗口级、无来源捕获。** 专注页那颗钮在休息时隐藏，因为那段时间没有任务上下文；
  但没有上下文只意味着不附带任务和科目，不是禁止捕获的理由——休息时也可能想到知识缺口。
  快捷键读的是和按钮同一个可用条件，休息计时不受影响。

## 快捷键默认值的定法

- **默认键位的理由只有两条：交互约定与冲突检查。** 交互约定指「相邻键位不该对应产物完全不同
  的动作」（`gap.capture` 不取 ⌘⇧N，就因为它是「新建任务」⌘N 的近邻，而知识缺口的常态
  恰恰是还定不了什么时候处理，挨在一起诱导按错；⌘⇧K 在默认表里空着，K 取自 knowledge）。
- **某个键位被现有测试用着，不是改产品默认值的依据**——方向反了，该改的是测试。
  `ShortcutRegistryTests` 里「随便换一个键位」类用例统一用 `kSpareSequence`
  （`Ctrl+Alt+Shift+Y`）：三修饰符加字母，不在默认表里，也不会成为任何产品默认值，
  因为应用内默认一律 ⌘ 或 ⌘⇧ 打头。借用真键当样本，会让以后给新动作定默认键位时撞红这些用例，
  看起来却像「那个键不能用」。
- 冲突与默认值本身另有专门用例覆盖（`assignRejectsConflictWithAnotherActionInAnyScope`、
  `resetAllRestoresEveryDefault`），不靠样本键顺带验证。

## 科目下拉的内联新建

- `AddTaskDialog` / `EditTaskDialog` / `GoalFormDialog` 的科目下拉末尾挂一条编号为 `-2` 的哨兵
  「+ 新建科目…」。它**不是科目**：选中后立刻把下拉退回上一个真实项再开新建框，
  取消时下拉不能停在哨兵上。提交路径另有一道闸把 `-2` 收敛成 `-1`，防止哪条路径漏了退回。
- **恢复点记科目编号（`lastRealCategoryId`），不记下标。** 科目按 `display_order`、`name` 排序，
  增删、改名都会让已选科目换位置，旧下标可能指着别的科目、甚至正好指着哨兵本身。
  恢复点那个科目不在了就回到「不设置科目」/「未选」，绝不停在哨兵上。
- **每次打开把恢复点同步成这一次的初始选中**，不继承上一次打开时记下的科目。
  新建任务弹窗此前只在关闭时把下拉复位、恢复点没复位：上次存在「英语」下，这次点哨兵再取消，
  下拉会跳回用户这次根本没选过的「英语」。
- `GoalFormDialog` 的 `categories` 末尾含哨兵，因此「选中的是不是合法科目」一律用
  `realCategoryCount` 判（`hasRealCategorySelected()`），不能再用 `categories.length`。
- 内联新建只收名字，颜色按已有科目数量在 `ColorPicker` 那份暖色阶里顺位取——
  建任务建到一半想起要分个新科目，此刻要的是别打断，不是再做一次配色决策。改颜色仍走科目管理。
- 建完自动选中新科目；`CategoryManager::addCategory` **先发 `categoriesChanged` 再返回编号**，
  QML 替身必须按这个时序写（`tst_inline_category_sync`），顺序反过来会让「收到信号时新科目还查不到」
  这类问题在测试里消失。
- **弹窗开着时科目在别处变了，四个带科目下拉的弹窗都要跟着刷新**：`AddTaskDialog`、`EditTaskDialog`、
  `GoalFormDialog`、`KnowledgeGapDialog` 都订阅 `categoriesChanged`，先记下当前选中的**科目编号**再重建下拉、
  按编号选回去；原科目被删了就回落到「不设置科目」（目标表单为未选、知识缺口为「不指定」），
  不能停在别的科目或哨兵上，更不能把被删的编号照样提交出去。
  是否订阅不看「现在有没有入口能在弹窗开着时改科目」——没找到入口不等于入口不存在，验收要的是行为本身。
  新建、编辑任务弹窗的门禁写在 `onCategoriesChanged` 处理函数里（`root.visible`），不用 `enabled` 绑定；
  关着时不刷，打开时本来就会刷。
  自己建科目时服务先发信号再返回编号：开着时的刷新先保住当前选中，`onCreated` 随后再选中新科目，
  两段的先后由 `tst_inline_category_sync` 按真实时序覆盖。
- 预设科目由 `DatabaseManager::insertPresetCategories()` 播种（5 条，`is_preset = 1`），
  每次打开库都会跑，靠 `display_order` 作稳定身份幂等（用户改名改色后不会再复制一行）。
  **内联新建不碰这条路径，也不放开预设科目删除**——后者是数据策略变更，涉及删除 SQL、
  `canDeleteCategory()`、界面按钮门禁，以及补种逻辑需要墓碑标记（否则删掉的下次启动会复活）。

## 本周计划的合计与键盘导航

- 每天给出「已排 N」（当天全部任务预计用时之和，完成与否都算——问的是「排了多少」，
  与今日任务页 `plannedMinutesToday` 同一口径），副标题给出本周合计。一条都没排时长的日子
  不显示「已排 0 分钟」，那不是信息是噪音。
- 已完成的任务沉到当天末尾，**同一完成状态内保持服务层给的原有顺序**
  （`display_order`、创建时间、编号）。用两趟稳定分区而不是 `sort`：加一个二次排序键
  就会悄悄改变同组内的相对位置。
- 外层 `ListView` 的 `model` 是 7（一项一天），任务在内层 `Repeater` 里，
  所以 `ListView.currentIndex` 选中的是**天**不是任务，不能拿来当游标。
  游标记的是**任务编号**：下标在任务增删、以及完成后沉底重排之后指向的就是另一条任务了。
  按编号记，完成一条之后焦点自然跟着它挪到当天末尾。
- 摊平序列 `flatTaskIds` 按「天序 + 天内序」生成，空日子不产生条目，↑↓ 因此天然跳过它们。
  到首尾就停，不循环——一路按下去从周日绕回周一会让人失去位置感。
- 删除后的落点逐级尝试，取第一个命中的：**当天后继 → 当天前驱 → 后续非空日首条 →
  前序非空日末条 → 清空**。中间两级最容易漏：删掉当天最后一条但当天还有前序任务时应落到前驱，
  删掉全周最后一条但前几天还有任务时应落到前序非空日末条。落点必须在**发出删除请求之前**算好，
  请求一发出宿主就把那一行从模型里藏起来了。
- 刷新后按编号恢复游标，目标任务已不在则清空，不留一个指向空气的游标。
  游标滚动定位先用 `positionViewAtIndex(dayIndex, ListView.Contain)`——外层是虚拟化列表，
  屏幕外的 delegate 根本没被创建，不能靠累加 delegate 高度定位。**只按天定位不够**：
  一天比视口高时 `Contain` 把这一天顶到视口上沿，当天靠后的任务仍在视口外
  （12 条的一天，第 12 条落在 562px 视口的 957px 处）。所以再按任务行在内容坐标里的下沿补一段日内偏移。
  只需往下补：`Contain` 之后比视口高的一天上沿贴着视口上沿、比视口矮的一天整个可见，行不会跑出上沿。
  `tst_week_logical_day` 用真实按键量行在视口里的位置，覆盖「一天超高」与「跨虚拟化的日子来回走」。
- 「已排」是否显示暴露为 `showsTotal`，副标题有 `objectName: weekSummaryText`：
  测试断言这两个，不断言会沿父链级联、离屏下不可靠的 `visible`。
- macOS 笔记本主键盘上写着 delete 的那颗发的是 `Key_Backspace`，删除必须同时接管它；
  只认 `Key_Delete` 等于这条通路在本应用唯一的目标平台上不存在。
- **键盘入口要主动交接。** 列表上的 `focus: true` 只在所在焦点域拿到焦点时才生效；
  鼠标点侧栏切页时，侧栏条目会把焦点留在自己身上（`Sidebar.qml` 为了让 Tab 从当前项继续），
  于是 ↑↓ 等按键全部落空。所以本页可见且激活时（`keyboardEntryReady`）把焦点交给列表；
  点任务行时游标落到这一行并交接焦点。输入框正在编辑、或弹窗占着焦点时不抢。
  点行的 `TapHandler` 挂在本页的 `TaskItem` 实例上，不改 `TaskItem` 本身（今日任务页也用它）；
  它与任务行自带的 `DragHandler` 共存，按住拖动仍由拖动接管，拖完不会被当成一次点击去改游标。
- **键盘相关的用例必须发真实点击与按键**（`tst_week_keyboard_entry`，`TestCase` 需 `visible: true`）。
  此前的用例全部直接调 `moveCursor`，游标逻辑是对的，却从没发现用户那条路径上按键根本进不来。
- **能不能从某条开始专注只有一个口径**：`canStartFocusFor(taskId)`——今天那一行、且没完成。
  键盘回车与行内「开始」按钮都读它，此前两边各写一份，回车漏判了已完成。
  完成后到列表重载之间（完成动画要播完，重载推迟约 850ms）模型里的 `completed` 还是旧值，
  所以用 `completionOverrides` 记下刚改过的完成态、重载后清空，否则回车能趁这个窗口启动刚完成的任务。

## 热力取档与专注历史月历的投入条

- **分钟数 → 档位只有一个函数**：`qml/HeatmapBands.js` 的 `bandForMinutes`。零投入单独返回 `NONE`，
  正投入按绝对分钟数分四档 `< 60 / 60–149 / 150–299 / ≥ 300`。不按「占当月最大值的比例」分——
  那会让整月都学得少的月份照样染出最深的一天。目标详情热力图（`GoalHeatmap`）与专注历史月历
  都调用这个函数，不要另写一份阈值。
- **共用的是映射函数，不是输入数据。** 目标详情统计某一个目标的投入，专注历史统计当天全部投入；
  同一天数学 90 分钟、总计 330 分钟，分别落第 2、第 4 档是正确结果。回归要守的是
  「同一个分钟数在哪一页都落进同一档」，不要断言「同一天在两页同色」。
- 调用方传 `seconds / 60`，**不要先取整**：30 秒取整成 0 会被画成零投入，同一格的时长文字却显示有记录。
  `bandForMinutes` 用 `!(value > 0)` 判零，NaN、null、非数字一律按零投入——
  写成 `value <= 0` 挡不住 NaN，它会一路漏到最深那档。
- 颜色只在 `Theme.qml`：`heatmapBandColors`（浅深各四档）与 `heatmapEmptyTrack`。
  **浅深两套方向相反**：浅底投入越多越深，深底投入越多越亮；把日间色阶直接搬到深底，
  最低档会是近白块、比高投入还抢眼。判据由 `tst_heatmap_bands` 写死：相邻两档 CIEDE2000 ≥ 7，
  空轨道在普通 / 选中 / 悬停三种格底上都 ≥ 5、与第 1 档 ≥ 5、且在普通格底上比第 1 档安静。
  调色前先跑它。
- **专注历史月历用格底投入条，不整格铺色。** 这页格子高约 78、宽随窗口变（1200 宽窗口下约 154；目标详情是 59×38），
  每格本来就有 1px 描边、有两行文字，而且选中与悬停改的就是底色。整格铺色会色块压过整页，
  并被选中态的 `accentSoft` 整个盖掉（4 档那天反而成了全月最浅的一格）。
  所以底色继续归选中 / 悬停 / 今日状态，投入强度只由格底 8px 色条表达；文字始终在中性底上，
  沿用 `ink` / `accentFillInk`，不需要逐档文字色。
- 四种格子：有投入 = 按档着色的条；零投入（含今日零投入）= 空轨道；未来 = 不画条；
  本月之外 = 什么都没有。未来按**逻辑今日**逐格判断（年月日拼整数比，不比 Date），
  翻到将来的月份整月都是未来，翻回过去整月都不是；跨过日界时，原先的「明天」立即开始画条。
- **空轨道不复用 `Theme.border`**：它压在选中底 `accentSoft` 上 ΔE00 只有 2.2（夜间 3.2），
  被选中的零投入日会被读成「没有轨道」即未来——本月内的未来日同样能点选，两态会同时出现。
  `heatmapEmptyTrack` 是热力专用令牌，不要为了它去改全局 `border` 或 `surfaceSunken`。
- **未来日期不降色**，保留 `Theme.ink`：降为 `inkMuted` 后夜间退得过深，像是不可操作，
  而这些日期实际能点击；未来已经由「不画投入条」表达，不需要再牺牲日期可读性。
- 格内日期与时长**靠顶排**，不铺满整格：`ColumnLayout` 铺满时会把两行纵向摊开，
  时长那行被推到格底贴住投入条，有无时长的格子日期高度也会跳。`tst_month_heatmap_bar`
  在卡片允许的最矮高度下断言两者之间留有间隙。
- **目标详情热力图整格铺色**（格子 59×38，只有日期一行，也没有选中态，和专注历史那页的约束不同）。
  `getGoalDailyCounts` 的 `count` 字段是**分钟**（有效会话 `SUM(duration)/60`），不是番茄数；
  读屏与悬停提示按分钟报（`Duration.format`），不能再说「N 个番茄」。
  色值是不透明纯色，不叠 `opacity`：规格色就是屏幕上那个色，`tst_goal_heatmap_bands` 按像素核对。
- 目标详情热力图的五种格子，逐格按调用方传入的**逻辑今日**判（年月日拼整数比），不看整月：

  | 格子 | 表现 | 播报 / 悬停 |
  | --- | --- | --- |
  | 过去 · 零投入 | 零值底色 `surfaceSunken`，无描边 | 无投入 |
  | 今日 · 零投入 | 零值底色 + `accent` 2px 今日标记 | 今日暂无投入 |
  | 有投入（含今日） | 对应档底色 + 对应档字色；今日另加 `accent` 2px | 投入 N 分钟（今日带「今天」） |
  | 未来 | 不填色，`Theme.border` 1px 实描边 | 尚未到来 |
  | 本月之外 | 完全空白，无描边 | 不播报 |

  不存在「全零月份」状态，也不再有除以当月最大值。
- **逐档字色**是 `Theme.heatmapBandInkColors`，写死色值、不引用 `inkStrong` / `surface`：
  每档只从两种字色里取，在这组字色下中间一段亮度两种都不达标，所以色阶非等距——
  这条结论只对这组字色成立。每档 ≥ 4.5:1 由 `tst_heatmap_bands` 断言。
- **零投入与未来格的日期保留 `Theme.ink`，不降成 `inkMuted`**：`inkMuted` 在零值底上日间只有 2.88:1、
  在页面底上 3.31:1，夜间 4.35 / 3.95，都不到 4.5:1。零值的「安静」由底色表达，未来由描边表达，
  都不需要牺牲日期可读性（与专注历史「未来日期不降色」同一理由）。
- **过去零投入与未来的区分落在未来格那圈描边上**：零值底色对页面底只有 ΔE00 4.8、夜间 2.6，
  单靠「填了没填」分不开。描边调细到 `borderSubtle`（夜间 5.1）两态会合并。
  零值格偏弱是定案（热力图先突出投入强度），真实使用中若认不出零值，加专用 `heatmapZeroBackground`，
  不要改全局 `surfaceSunken`——它还被输入框和次级容器用着。

## 数据安全与跨层交互

- schema 版本以 `DatabaseManager::kCurrentSchemaVersion` 为准。迁移不能只信版本号，还要检查结构，补齐缺失的表或列；已有但不合法的课表结构须报错。空节次表重新打开时补默认节次，失败必须整体回滚。
- 课表主键必须具备 SQLite 自动生成整数编号的语义；启动与备份检查共用校验。v13 备份必须有合法课表表、约束和主键，旧版本备份允许缺表，由恢复后的迁移补齐。
- 旧备份兼容性按 schema 版本判断，不能把后续新增或懒建的表无条件加入所有版本的必需表清单。增加任务列时同步检查 `migrateToVersion5` 的整表重建语句与列清单，避免重建丢数据；迁移测试要覆盖带旧数据的数据库。
- 备份拒绝 Trigger、View、虚拟表等非预期数据库对象；恢复设置仅写回 `AppSettings::ownedSettingGroups()` 声明的顶层分组，兼容快捷键等动态子键。新增设置分组必须同步所有权清单。恢复走 `AppSettings::reload()` 重建设置后端，新增带 NOTIFY 的属性必须在那里补发变更信号，否则恢复后 getter 已是新值、界面却停在旧值直到重启；`appSettingsReloadNotifiesEveryProperty` 按元对象逐个属性核对。
- 新恢复点创建并提交成功后再清理旧快照，失败不能提前消耗最后的恢复机会。恢复失败需要回滚并重新打开数据库；数据库替换期间阻断界面操作、快捷键与直接动作分发。
- CSV 导出、备份和恢复的耗时工作放在工作线程。数据库连接不跨线程共享，导出线程使用独立只读连接；全部导出的多个文件读取同一事务快照。导出期间的关闭、取消、退出语义必须一致。
- 主连接的锁等待设置、后台连接与事务边界协同维护；不能用界面假成功掩盖写入失败。失败状态要保留可重试入口，与正常空数据区分。
- macOS 原生实现放在 `src/platform/macos`；业务服务依赖平台无关抽象。跨服务信号在组装层接线，避免目标服务与计时器形成循环依赖。
- 本机部署使用暂存包、旧包备份与原子切换，失败还原旧包。具体命令与二进制一致性校验见 [运行命令](运行命令.md)，协作约束见 [AGENTS.md](../AGENTS.md)。

## 界面与验证约定

- 使用现有 `Theme.qml` 语义颜色与 Qt Quick Controls 风格；独立弹窗也须接管 `palette`，保证浅深主题中的正文、占位文字、选区及输入边界可读。
- 玻璃效果只用于导航、浮动工具栏、弹窗与重要控制，内容卡保持清晰；业务内容位于光学层之上，效果缺失或关闭时提供可读的半透明纯色降级。不可见时停止效果更新，动效支持 `reduceMotion`。
- 调低 `MultiEffect.blurMax` 会同时改变阴影外观，不能把它当成无副作用的性能参数。性能改动先提供测量，不能仅凭组件数量决定虚拟化或切换渲染实现。
- 非字面量 `text` 绑定必须显式声明 `textFormat`，避免任务标题等字符串被 AutoText 猜成富文本，由 `QmlTextFormatGate` 检查。
- `QmlLintGate` 负责静态告警；类型推导限制只允许在具体表达式旁注明原因并局部压制，不能全局放宽类别或数量。
- 每个 QML 测试条目通过 `FAIL_REGULAR_EXPRESSION` 拦截 `Unable to assign`、`TypeError`、`is not a function` 与 `Binding loop`。确需触发告警的用例只调整自身条目，保留其他检查。
- 运行时门禁只能覆盖实际执行的路径。弹窗测试需真正打开并执行交互，`tst_dialog_smoke.qml` 提供基础覆盖；不能把仅实例化组件当成完整覆盖。
- 注入的服务替身缺方法或属性时，先检查可调用性，再显式归一化布尔和数值；仅检查对象非空不能避免运行时类型错误。
- QML 里数值回退不能写成 `value || 默认值`：优先级「低」是 0、日界可以是 0 点，`||` 会把合法的 0 当成缺值。只在 `undefined`、`null` 或空串时才回退。测试替身不要同时声明 `signal fooChanged()` 与 `property foo`：属性自带同名变更信号，整个测试文件会编译失败。
- 焦点环只能由 `Control.visualFocus` 驱动，不能用 `activeFocus`：窗口切走再切回、弹窗关闭把焦点还回来时 `activeFocus` 同样从假变真，于是鼠标点过的那一项会亮起焦点环，和当前选中项一起出现两个框。需要焦点环的自绘条目（如侧栏条目）根用 `Control`，外观读数用 alias 留在条目上供调用方与测试读取。
- Basic 风格的竖向滚动条贴着 `ScrollView` 右缘浮在内容上，`ScrollView` 不会替它让位：带滚动的页面必须自己留出 `rightPadding`，否则最右一列控件被压住。不要绑 `effectiveScrollBarWidth`——它随「内容是否超出一屏」变化，而内容高度又受可用宽度影响，会绕成绑定循环。
- 日期一律用年、月、日三个整数拼 `yyyy-MM-dd`，不要把 `MonthGrid`、`QDate` 给的 `Date` 直接格式化：那条路带时区换算，可能整体差出一天。可选日期的字段用 `DatePill`（点开选、留空是常态），必填且需要手输或逐日调整的字段用 `DateInput`。
- 配色是否可用，判据是**对比度**与**色差**，不是亮度差。`0.299R + 0.587G + 0.114B`
  只说明两个色在明度上分开了，既不回答「相邻两级人眼分不分得出」，也不回答
  「上面的文字读不读得出来」——用它当唯一判据会漏掉「某一级的字根本看不清」
  和「最低一级和空值几乎同色」。承载文字的色块按 WCAG **4.5:1**（正文）核对，
  相邻级别的可辨识按 **CIEDE2000 ΔE00** 核对（≥5 才算不并排也看得出）。
- 禁区是**针对一组具体文字色算出来的**，不是色彩本身的性质。本项目的色块只在
  `Theme.inkStrong` / `Theme.surface`（浅色主题）与 `Theme.accentForeground` /
  `Theme.inkStrong`（深色主题）里二选一，在这组取值下，浅色主题相对亮度 0.17–0.33、
  深色主题 0.14–0.26 两种文字都到不了 4.5:1。**结论只到这里为止**：
  在当前文字色与暖色方案下，要同时满足对比度就得非等距取色。
  换一组文字色（例如给中间档单独配一个文字色）禁区会移动甚至消失，
  所以不要把它写成「多级色阶不可能等距」这种普遍命题。
- 自动验证使用离屏平台，不启动应用窗口；以状态等待代替猜测时长的固定睡眠，测试在初始化阶段复位数据库，避免单个断言失败污染后续用例。具体命令与测试约定见 [运行命令](运行命令.md)。
- `qmltestrunner` **按函数名字母序**跑用例，不按文件里的书写顺序。挂在整窗上的弹窗与展开态
  （捕获框、切换确认框、任务选择器等）必须在 `init` 里复位：某条用例展开后不收起，
  焦点就一直留在 overlay 里，后面按名字排在它之后的用例会被 `overlayHoldsFocus` 挡住而莫名变红。
  弹窗关闭有退出过渡，过渡期间焦点仍在 overlay 里，紧接着要触发快捷键的用例先等 `overlayHoldsFocus` 变假。
