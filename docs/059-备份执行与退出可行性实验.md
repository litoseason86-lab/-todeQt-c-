## 结论及授权边界

用户选择“要求双平台都达到相同硬期限；先完成可行性实验，再决定是否实施”。本阶段据此只验证候选机制，不将macOS子进程和iPad协作取消包装成同等保证。

当前候选方案不能满足“SQL或底层文件I/O永久不返回时，两个平台均在相同期限内安全停止所有工作并完成进程退出”的完整契约。macOS隔离执行器在已测故障中可以被终止并回收；普通iOS应用不允许自行创建同类子进程。独立SQLite连接能改善计算型SQL取消，却不保证打断尚未返回的系统I/O。主线程的设置写入、数据库重开与验证也仍在完整恢复链内，单独隔离VACUUM并不能约束整条链。

这是本轮机制的可行性判定，不是所有替代架构均不可能的证明，也不是059已修复。继续实施前必须决定如何界定期限覆盖的故障范围。当前未选定产品毫秒数；实验中的1秒和500毫秒仅是观测窗口。

## 动态结果

| 实验 | 前提与观察 | 结论及限制 |
|---|---|---|
| 当前QSQLITE能力 | 对实际驱动调用hasFeature(CancelQuery)，返回false | 不能靠通用cancelQuery接口承诺取消；本项运行于Mac |
| 旧服务退出 | 注入任务已进入不返回的信号量等待，握手后调用prepareForShutdown；1秒内无返回 | 确认现有服务等待依赖任务完成；测试父进程最终杀回收，不是产品自身有界退出 |
| 跳过服务等待的对照 | 相同任务，跳过服务等待；已打印SERVICE_RETURNED，但进程1秒内仍未退出 | 仅删除waitForFinished仍被全局线程池析构等待，不能算修复 |
| 对基础future调用cancel | 相同任务，在退出前调用watcher.cancel；有取消请求标记，仍未退出 | 基础QtConcurrent任务没有因此被强制终止 |
| 真实备份持锁，3轮 | 真实服务初始化隔离数据库；父进程BEGIN EXCLUSIVE后派发requestBackup，再调用退出；1秒内未退出，父进程释放锁后完成 | 释放锁后正常结束，原库与备份integrity_check均为ok；结果中的完整观测耗时包含退出后的完整性检查，不当作退出延迟。这是可恢复锁等待，不是永久内核I/O复现 |
| 独立进程长SQL/阻塞读/阻塞写，各3轮 | 使用真实长SQL计算及无数据/满管道，握手后确认200毫秒内不退出，再SIGKILL并wait回收 | 9次均成功回收，信号到回收小于2毫秒；只是当前主机样本，不是产品期限或永久文件系统I/O保证 |
| 独立SQLite长SQL取消，各3轮 | 递归查询已进入执行，再发interrupt或设置进度回调的取消标记 | 6次均返回SQLITE_INTERRUPT；取消握手后到进程结束均小于1毫秒，不作为跨平台性能承诺 |
| 独立SQLite阻塞读，interrupt，3轮 | SQL函数已进入管道read，再调用interrupt | 500毫秒内未返回；父进程明确放行read后才返回SQLITE_INTERRUPT，证明取消不等于系统读已结束 |
| 独立SQLite阻塞读，进度回调，3轮 | 相同阻塞读，仅设取消标记 | 500毫秒内未返回；放行后查询甚至正常返回，期间进度回调调用数为0。执行器还必须独立检查取消状态，不能只依赖SQL错误码 |
| iOS原生探针编译 | 相同SQLite取消探针以arm64-apple-ios26.0编译并链接系统libsqlite3 | 成功、无编译告警；Mach-O平台记录为IOS。没有真机执行，不代表iPad运行验证通过 |

上述SQL函数内的管道读用来构造确定不返回的系统调用边界；它不是本项目使用了该函数，也没有模拟SQLite VFS真实磁盘读写。信号量实验同样属于受控故障注入。不能把它们改称真实iCloud卡死、磁盘满或iOS生命周期实测。

## 平台与库的契约核对

本机Qt6.10.3的iOS `qtcore-config.h`将`QT_FEATURE_process`设为`-1`，Mac为`1`。这首先证明当前工具链没有QProcess执行器能力；普通iOS应用不能自行创建子进程的系统限制另由[Apple DTS的说明](https://developer.apple.com/forums/thread/747499)支持，不能只凭SDK仍声明fork/posix_spawn就推断普通应用有执行权限。

[SQLite interrupt契约](https://sqlite.org/c3ref/interrupt.html)是尽早在可中断机会返回，并没有强制解除任何系统调用的期限。[进度回调](https://sqlite.org/c3ref/progress_handler.html)依赖SQLite执行机会，不是操作系统I/O取消接口；本轮阻塞读结果与这一边界一致。

[Qt6.10线程终止文档](https://doc.qt.io/qt-6.10/qthread.html#terminate)说明强制终止线程可能打断修改并留下未释放的锁，且不承诺立即终止。不能把terminate、泄漏线程/线程池、跨库操作Qt SQLite句柄作为修复。

[Apple后台任务接口](https://developer.apple.com/documentation/uikit/uiapplication/beginbackgroundtask(expirationhandler:))要求期限到达前结束后台任务，超时可能被系统终止；它不是SQL或文件I/O取消器，也不构成应用可控制的安全退出期限。当前`IosBackgroundTask`仅服务同步且过期时结束token，没有中断BackupService工作。没有在真机触发过期回调。

## 全链路副作用与取消边界

| 阶段 | 现有实现与副作用 | 期限与安全性必须覆盖的点 |
|---|---|---|
| 创建备份 | BackupOperations::createSnapshot：独立Qt连接、VACUUM临时库、嵌入设置、全量校验、原子发布 | SQL计算、读库、写临时库、偏好读取、校验、最终commit；发布前取消保留旧目标，发布后结果丢失不能假定未提交 |
| 读取备份信息 | inspectBackup：只读连接、预算扫描、integrity_check、结构和计数查询 | 不改主库，但SQL与I/O仍能阻塞；主机线程超时不能安全销毁尚在执行的连接 |
| 恢复预检 | requestRestore：先读当前设置并准备持久化意图，再后台复制到受控副本、校验、读嵌入设置 | 预检未换主库；只有确认工作已停止且原库/设置未变化才能判安全取消；受控副本不能在worker仍访问时删除 |
| 恢复前快照 | installPreparedRestore先关主库，再后台生成恢复点 | 成功创建新恢复点才清理历史；取消或结果丢失时不能用“路径存在”猜已完整创建 |
| 安装 | 后台atomicCopy覆盖主库；主线程initialize、验证、清备份表、写设置和恢复计时 | 原子rename前后语义不同；无法确认提交点就保留prepared及同步阻断。主线程重开/迁移/设置同步也不受子进程期限保护 |
| 回滚 | 关闭库、后台复制恢复点、主线程重开验证并恢复原设置/计时 | 拷贝成功不等于设置回滚成功；超时不属于safeToResume，不能在仍有写者时重开或删恢复点 |
| 退出 | AppLifecycle按草稿、待删项、计时、备份、同步、关库顺序执行 | 不能只让函数返回而留下访问SQL插件、设置或QObject的线程；后台任务不是唯一可能等待的节点 |
| 重启 | SyncController读取prepared/installed日志，未完成意图阻断同步与自动清理 | 059若改变安装过程，必须逐截面验证日志、数据库和偏好一致；现有日志不能凭worker超时自动升级为installed |

本轮未运行安装中断、原子提交边界、回滚超时或重复/丢失结果的产品回归，因为尚未批准可实施的执行器契约；这些保留为实施验收条件。

## 下一阶段的决策与实施前提

保持当前完整硬期限要求时，059不能按现有候选方案直接落地并宣布达标。需要先接受以下一项决策：

1. **保留原要求，暂不实施。** 原风险继续保留；未来有可用的平台隔离或可证明中断能力时再评审，不能用等待系统杀进程替代。
2. **缩小共同契约后实施。** 双平台统一覆盖可控SQL计算、操作间检查点、未提交结果拒绝与恢复日志保护；永久内核I/O和完整进程退出仍明确未达标。届时再评审独立SQLite连接、分块复制和生命周期策略，分别提出取消响应、执行预算与退出预算，不能共用一个含糊的“超时”。本报告不等于已经授权这个范围变化。

不建议为满足一个表面时间数字强制终止整个正式应用。那会改变草稿落盘、数据库与设置一致性、生命周期和用户体验，不能沿用“安全退出”名称。

契约获准后，执行顺序为：固定错误/取消结果与操作身份 → 建立每阶段确定性父进程回归 → 引入执行器接口及平台装配 → 改预检/快照/安装/回滚 → 逐截面验证持久化保护与重启 → 完整Mac/iOS构建及全量CTest/Swift → 单列真机生命周期验收。不提前新建子进程产品目标或改主线程恢复链。
