## 一、先定原子单位

TRACK 100 的一切奖励都锚在「打卡 +1」这一个动作上。番茄 Todo 里已经存在等价的原子动作：

> **一个有效番茄** = `focus_sessions` 中 `mode = 番茄模式` 且自然到点的记录。

这个口径在 `FocusTimer.cpp:38` 和 `TaskManager::getCompletedPomodorosForTask` 里已经统一，直接复用，**不新增第二套计数**。

好处：用户不需要为了「长期目标」多做任何操作。专注结束的那一刻，进度自动推进 —— 比 TRACK 100 手动点「打卡」还省一步。

## 二、新增概念：长期目标（LongGoal）

现有三类对象里没有「带数量的长期目标」这一格：

| 已有 | 是什么 | 缺口 |
|---|---|---|
| `Task` | 挂在某一天的待办 | 生命周期只有一天 |
| `CountdownGoal` | 到某个日期还剩几天 | 只有时间，没有数量、没有进度 |
| 每日专注目标（`AppSettings::dailyFocusGoalMinutesForDate`） | 当天专注分钟数 | 每天清零，无累积感 |

**LongGoal 补的是「跨月累积 + 可视化进度」这一格。**

### 2.1 关键决策：进度不落库，纯派生

TRACK 100 最值得抄的一点是 `localStorage` 里只有 `logs[]` 时间戳数组，进度/等级/热力图全是纯函数算出来的，**不可能出现奖励状态和真实数据对不上**。

对应到本项目：**LongGoal 只存"筛选条件 + 目标值"，不存已完成数量。**

```
LongGoal = (科目 category_id, 起始日期 start_date, 目标番茄数 target_pomodoros)
进度 = SELECT COUNT(*) FROM focus_sessions
       WHERE mode = 番茄 AND 自然到点 AND 逻辑日 >= start_date
         AND task_id IN (SELECT id FROM tasks WHERE category_id = ?)
```

带来三个直接收益：

1. **零同步 bug**。删掉一条专注记录，进度自动回退，不需要任何补偿逻辑。
2. **历史自动回填**。新建「英语 · 100 个番茄」时，如果 `start_date` 填过去的日期，已有记录立刻算进去 —— 首次打开就有进度，跨过冷启动的空窗期。
3. **零迁移风险**。`focus_sessions` 一列都不用加。

代价：目标必须绑定一个科目，无法表达「读完 30 本书」这种和专注无关的目标。这个取舍我认为值 —— 番茄 Todo 是专注工具，不是通用习惯打卡器。

> 二期若确实需要非专注型目标，再给 `focus_sessions` 加 `goal_id` 可选列，走 A 方案。**现在不要预留**，预留的列一定会先腐烂。

### 2.2 数据库：schema v8

```sql
CREATE TABLE IF NOT EXISTS long_goals (
    id INTEGER PRIMARY KEY AUTOINCREMENT,
    title TEXT NOT NULL CHECK(length(trim(title)) > 0),
    category_id INTEGER REFERENCES categories(id) ON DELETE SET NULL,
    target_pomodoros INTEGER NOT NULL CHECK(target_pomodoros > 0),
    start_date TEXT NOT NULL,              -- 逻辑日，yyyy-MM-dd
    deadline TEXT,                         -- 可空 = 长期目标
    display_order INTEGER NOT NULL DEFAULT 0,
    fired_milestones INTEGER NOT NULL DEFAULT 0,   -- 见 3.2
    achieved_at TEXT,                      -- 首次达成 100% 的时间戳，可空
    created_at TEXT NOT NULL DEFAULT CURRENT_TIMESTAMP
);
CREATE INDEX IF NOT EXISTS idx_long_goals_order ON long_goals(display_order);
```

建表方式**照抄 `CountdownService` 的先例**（`CountdownService.cpp:303` 自建表），不进 `DatabaseManager` 的 `user_version` 迁移链 —— 纯新增表、无数据改写、无向后兼容包袱，走迁移链是过度设计。

配套说明：

- `DatabaseManager::kCurrentSchemaVersion` 保持 7 不变（因为没进迁移链）。
- **`BackupService::verifyRestoredDatabase` 的白名单不要加 `long_goals`。**
  初稿写的是要加，那是错的：该白名单校验的是「核心表必须存在」，而 `long_goals`
  是懒建表，早于本功能的备份里根本没有这张表，加进去会让**恢复旧备份直接失败**。
  `countdown_goals` 同样不在白名单里，保持一致。恢复后 `databaseChanged` 会驱动
  `GoalService::initializeDatabase()` 重新建表，旧备份恢复出来就是一个空目标列表，这是正确行为。

### 2.3 服务层：GoalService

新增 `src/services/GoalService.{h,cpp}`，单例 + `setContextProperty("goalService", ...)`，与 `CountdownService` 完全对称。

```cpp
// 增删改查
Q_INVOKABLE bool addGoal(const QString& title, int categoryId, int targetPomodoros,
                         const QVariant& startDateValue, const QVariant& deadlineValue);
Q_INVOKABLE bool updateGoal(...);
Q_INVOKABLE bool deleteGoal(int goalId);
Q_INVOKABLE bool reorderGoal(int goalId, int newIndex);

// 读取：一次聚合出所有目标的进度，避免 QML 侧 N+1 查询
Q_INVOKABLE QVariantList getGoals() const;        // 含 doneCount/percent/forecastDays
Q_INVOKABLE QVariantMap  getGoal(int goalId) const;
Q_INVOKABLE QVariantList getGoalHeatmap(int goalId, int year, int month) const;

signals:
    void goalsChanged();
    void milestoneReached(int goalId, QString title, int percent);  // 见第三节
    void operationFailed(const QString& message);
```

`getGoals()` 用**一条**带 `GROUP BY` 的 SQL 把所有目标的完成数一次算出来，不要循环里发查询 —— 参考 `StatisticsService::weeklyAggregates` 的批量聚合写法。

### 2.4 日期一律走逻辑日

TRACK 100 有个真实 bug：用 `toISOString().slice(0,10)` 取日期，是 UTC，UTC+8 用户在 00:00~08:00 打卡会被算到前一天，连续天数和热力图全错位。

本项目已有 `LogicalDayService` + `dayStartHour`，**GoalService 里所有日期比较必须经它换算**，不允许出现裸 `QDate::currentDate()`。这条要写进代码注释。

## 三、奖励机制：四层反馈

TRACK 100 的四层金字塔在本项目的对应实现：

| 层级 | 触发时机 | 本项目实现 |
|---|---|---|
| **即时** | 每个有效番茄结束 | 复用已有 `PhaseSoundService` 提示音；目标详情页在场时，100 格中新点亮的那格做 `scale 0.7→1.18→1` 弹跳 |
| **里程碑** | 跨越 25/50/75% | 新增里程碑提示音（三音上行）+ `CompletionParticles` 扩展版 + 轻量弹窗 |
| **达成** | 跨越 100% | 四音上行 + 粒子 + 弹窗 + 卡片转成「已达成」态 |
| **长期** | 目标数累积 | 等级 LV.1~5 + 已达成目标列表（见第五节，P2） |

### 3.1 触发点在 C++，不在 QML

**这是最容易做错的地方。** TRACK 100 在 React 的 `check()` 里比较前后值，因为它只有一个页面、永远在场。本项目里目标详情页大概率没开着，甚至可能在专注沉浸模式里，QML 侧比较必然漏触发。

正确链路：

```
FocusTimer 落库一个有效番茄
        ↓ focusCompleted 信号
GoalService::onFocusCompleted()
        ↓ 对每个未达成目标重算 percent
        ↓ 跨越检测 + 位掩码去重
        ↓ milestoneReached(goalId, title, percent)
MainWindow 全局监听 → 弹窗 + 音效 + 粒子
```

弹窗挂在 `MainWindow.qml` 顶层，**不挂在目标页**，这样在任何页面（包括仪表盘、专注页）都能弹。沉浸模式下应抑制弹窗、只留提示音 —— 里程碑庆祝不能打断正在进行的专注。

### 3.2 幂等：修掉 TRACK 100 的可刷 bug

TRACK 100 的 `undo` 只做 `logs.slice(0,-1)`，不记录已触发的里程碑，撤销 -1 再打卡 +1 就能无限重放撒花。

解法：`long_goals.fired_milestones` 位掩码。

```
bit0 = 25%   bit1 = 50%   bit2 = 75%   bit3 = 100%
```

判定逻辑：

```
for m in [25, 50, 75, 100]:
    if percentAfter >= m and not (fired_milestones & bit(m)):
        置位 → 写库 → 发 milestoneReached
```

注意这里**不比较 before**，只看「当前是否达标 + 是否已弹过」。这比 TRACK 100 的跨越检测更稳：

- 删掉几条专注记录导致进度回退，再涨回来，不会重弹。
- 一次性导入大量历史数据，只弹**最高**的那一档（实现时循环内取最大值，末尾只发一次信号），不会连弹四个窗。
- 用户在「编辑目标」里调小 `target_pomodoros` 导致瞬间达标，正常触发一次。

配套：编辑目标时若调**大**了目标值，`fired_milestones` 要按新 percent 重新计算并清掉不再成立的高位 —— 否则用户把 100 番茄改成 200，75% 那档永远不会再弹。这条边界要写进注释和测试。

### 3.3 音效与动效必须可关

- 音效走 `AppSettings::soundEnabled`，复用 `PhaseSoundService` 的资源加载与播放路径，不要新起一套音频后端。
- 粒子走 `AppSettings::reduceMotion`：关闭动效时只弹静态提示，不做粒子和缩放。
- 弹窗本身在 `reduceMotion` 下去掉入场动画，直接显示。

这三条是 AGENTS.md 的硬要求，不是可选项。

## 四、界面：分两页

### 4.0 两套版式 + 视图切换（已定）

目标列表同时提供**横向列表**和**三列网格**两种版式，用户可切换，选择跨启动记忆。

**头部布局**（这一页自己的版式，不动其它页）：

```
目标
把长期投入折成 100 格，看得见才坚持得下去

[进行中] [已达成] [全部]                        [☰|▦]
└─ 状态筛选：看哪些                    视图切换：怎么看 ─┘
```

两组控件语义不同，所以左右分开放、样式也不同（筛选是文字胶囊，切换是图标分段），
避免用户把它们读成同一组选项。视图切换只用图标不带文字，跟 Finder 的习惯一致。

**持久化**：`AppSettings` 新增 `goalViewMode`（`"list"` / `"grid"`），走 QSettings，
与 `sidebarVisible`、`dashboardTimerVisible` 完全同一套写法。

**图标**：`GlyphIcon` 已有 `grid`（科目管理在用），需要新增一个 `list` 字形（三条横线 + 左侧点）。

**要认的代价**：两套版式意味着空态、拖拽排序、响应式断点都要各做一遍，
之后每次改目标卡片都要改两处。实现时把「圆环 + 百分比 + 标题 + 副信息」抽成
共用的子组件，两套版式只负责排布，尽量把重复面积压到最小。

### 4.1 目标列表（新增侧栏入口「目标」）

现有侧栏已有仪表盘/今日/本周/专注/统计/倒数。新增一项，位置放在「倒数」之后 —— 倒数和目标都是长周期对象，聚在一起。

列表用现有卡片语言（`StatCard` 的圆角/描边/间距），每张卡片：

```
┌────────────────────────┐
│  ◯ 62%      英语精读     │
│             62 / 100 番茄 │
│             照此速度还需 21 天 │
└────────────────────────┘
```

- 圆环用现有 `FocusRing` 组件改造，或直接复用其绘制逻辑。
- **已达成态不加任何装饰性图章**（TRACK 100 的手写体 `done!` 是它的美术风格，和本项目的暖色克制风不搭）。改成圆环转成 `Theme.accent` 的完成色 + 副标题变成「已达成 · 7月14日」。
- 筛选：进行中 / 已达成，复用 `SegmentedSwitch`。按 `header-layout-feedback` 的定案，分段控件的位置沿用该页自身版式，不要顺手改其它页。

### 4.2 目标详情：100 格网格

```
英语精读                        [编辑] [删除]
────────────────────────────────
PROGRESS                62 / 100 番茄
▓▓▓▓▓▓▓▓▓▓▓▓░░░░░░░░

100 CELLS                        62%

■■■■■■■■■■  ← 第 25/50/75/100 格带描边
```

要点：

- **归一化**：`filledCells = min(100, doneCount / target * 100)`，目标 300 番茄时每个番茄推进 1/3 格，用 `width` 部分填充保证「点了有反应」。这是 TRACK 100 最聪明的一处，必抄。

## 五、成就树：明确降级为 P2，且要改造

TRACK 100 的胖胖树（10 个绿色圆 + 果实）是它的插画风格。按 `background-theme-aesthetic-feedback` 和 `apple-reference-warm-adaptation` 的定案 —— **忌卡通/贴纸感，不加插画** —— 直接照搬会被退回。

保留其中真正有价值的两点，丢掉美术形式：

1. **等级**：阈值照抄 `0/3/8/20/40`（前密后疏的对数曲线，新手三个目标就能升级）。名称用暖色语汇重写，不用「破土萌芽/参天大树」这套。
2. **完成目标的可回味性**：TRACK 100 点果实能看到「目标名 + 完成日期」。这个交互价值很高 —— 把奖励变成记忆锚点而不是计数器。改成统计页底部一条「已达成 N 项」的可折叠列表即可，一行一项，色点 + 标题 + 日期。

**不做树。** 若后续确实想要一个视觉化的收藏物，单独出设计稿再议。
