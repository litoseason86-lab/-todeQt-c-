# 059：协作取消与恢复保护验收报告

> 061补充：提交前复核发现Mac双SQLite运行实例的锁协调遗漏，现已通过应用专用同源Qt驱动及正式锁回归补修，详见[061验收报告](061-SQLite同源与写锁保护验收报告.md)。下文旧API来源证明只覆盖单连接，不再冒充跨运行实例安全证明。最新本地验收为CTest134/134、备份137/137，既有协作取消／重入与060保护继续通过；永久I/O和设备边界不变。

## 范围与结论

用户在可行性实验后批准第二方案：双平台实施共同的协作取消与恢复保护，永久系统I/O及完整进程退出硬期限继续列为未解决。本轮没有实施macOS独有子进程，也没有把后台系统终止当作安全退出保证。

代码已实现以下共同契约，最终构建与测试结果见末尾。默认单次操作处理预算为120秒，以单调时钟计时；这是请求协作停止的预算，不是保证函数或进程在120秒内返回。异步恢复的预检、快照和安装共享同一令牌；补救回滚有独立预算，避免原取消令牌让回滚必定失败。

## 最终行为

| 环节 | 本轮行为 | 保留的边界 |
|---|---|---|
| 操作身份 | 单次操作持有共享令牌，显式取消、预算耗尽和退出请求均可观察；异步完成回调核对当前身份 | 请求取消不会销毁仍在使用的对象 |
| SQL计算 | 备份用自己创建的SQLite C API连接；进度回调检查取消，锁等待回调同时检查取消 | 不能中断尚未返回的系统I/O；主业务Qt连接不安装这些回调 |
| SQL兼容 | 窄范围QSqlDriver适配器复用现有QSqlQuery、表结构/外键校验、资源预算及历史设置序列化 | 适配器只服务本项目备份操作，不是通用SQL驱动替代品 |
| 文件复制 | 每个1MiB块及原子提交前检查令牌；取消前已写暂存数据也不覆盖旧目标 | 提交中的系统调用仍可能阻塞 |
| 提交事实 | 结果分别记录success与committed；提交后取消不再伪称目标未动 | 取消不保证一个已经完整提交的备份文件不存在 |
| 备份与信息读取 | 取消或超预算不报告成功/有效；自动备份取消不推进成功时间、不触发历史配额清理 | 工作真正结束前busy与既有恢复遮罩继续保留 |
| 恢复安装 | 未提交主库时取消可安全结束；主库已提交时使用独立令牌回滚 | 初始化、验证及设置写回仍有同步等待，不能承诺全链路硬期限 |
| 恢复回滚 | 回滚未完成或超预算时safeToResume=false，保留prepared与同步阻断；原恢复点保留 | 数据库能重新打开不等于数据库与偏好属于同一截面 |
| 退出与重启 | 先请求取消，再等worker实际结束；安装已提交但收尾未完成时退出，不发送虚假成功，重启仍识别prepared | 永久I/O依然可能拖住退出，未泄漏线程池或强杀正式应用 |
| 生命周期 | Hidden/Suspended请求取消；Inactive/Active不取消，分屏失焦不误伤 | 未在真机验证系统挂起及后台到期时序 |
| 同步入口 | 同步手动／自动／替换前快照及恢复在完整生命周期内占用准入；准备回调与恢复内部收尾同样受保护 | 属性先整体更新再通知，通知重入后旧流程不覆盖新任务；未改变备份文件格式、数据库schema或设备同步协议 |

## SQLite连接及链接边界

连接始终由备份适配器自行创建和持有，不使用Qt QSQLITE的native句柄，也不从主线程调用worker的SQLite连接。主线程只写共享的原子取消状态。

实际二进制核对覆盖适配器调用的全部27个SQLite API：Mac均导入libsqlite3；iOS静态链接后均解析为同一可执行文件内的SQLite定义，与Qt静态打包有关，没有一部分API走动态库、另一部分走静态实现的混合。不能简单把双平台实现统称为“系统SQLite连接”。该核对是编译和链接证据，不是iPad运行证据。

PTCore新增私有SQLite::SQLite3依赖。ArchitectureGate只增加核心层这一明确例外；合成依赖清单分别证明：PTCore原生SQLite放行，PTCore链接QML、PTApp直接链接SQLite和未知原生依赖仍拒绝。没有扩大PTApp/PTQml白名单。

## 回归与有效红灯

新增回归先证明问题，再验证保护有效。编译失败不算红灯；父进程护栏不是产品期限。

- 修复前，入口取消仍创建复制目标、耗尽预算仍把备份判为有效；两项用例实际失败。
- 服务层接线前，显式取消的异步备份和恢复仍报告成功；两项用例实际失败。
- 生命周期接线前，Hidden未设置取消状态；用例实际失败。
- 同步入口准入修复前，异步操作期间createBackup仍成功创建第二份备份；用例实际失败。
- 移除复制提交前检查：旧目标被新内容替换，提交事实断言失败。
- 移除SQL进度取消：有限但足够长的递归SQL正常返回，取消断言失败；不是靠无限SQL把测试挂死。
- 清除已提交事实：主库提交后取消没有恢复原数据，真实任务数断言失败。
- 移除退出取消请求：父进程先确认worker已进入SQL检查点，再观察子进程不能正常退出；父进程回收该测试进程，测试框架本身未超时。

最后四项受控变异均构建成功后取得有效红灯，并按原字节/SHA恢复。随后新增同步准入守卫属于后续正常修改，最终受控源码另存SHA清单，不将变异基线SHA误称为最终所有文件SHA。

恢复专项覆盖预检复制后、恢复点提交后、主库提交前、主库提交后、回滚复制失败、回滚预算耗尽。断言真实任务/设置值、恢复点、safeToResume及重建控制器后的恢复保护；另有安装已提交但未收尾时退出的持久化截面回归。现有Qt6.9完整兼容夹具、WAL备份、资源上限和外键校验回归继续运行。

## 构建中的问题及处理

1. iOS缓存仍引用已经移除的iPhoneOS27.0 SDK。只清理指向该失效SDK的八个检测缓存键，再用当前27.1 SDK配置；随后发现编译器隐式链接路径也仍指向旧SDK，备份并重新生成三份编译器探测信息。未删除构建目录或改变SDK安装。
2. FindSQLite3的SDK系统头目录作为显式搜索路径后，使Xcode27.1的libc++包装头查找失败。该目录由sysroot隐式提供，CMake仅在SDK的usr/include场景移除重复的导入include属性。没有关闭编译错误或修改SDK头文件。Xcode在一次构建中执行ZERO_CHECK重新生成工程后仍使用旧响应文件，下一次完整命令才读取新工程；失败记录保留，不当作成功验收。
3. 首轮完整CTest为132/133，唯一失败是架构门禁拒绝新依赖。按实际分层更新核心白名单，并验证不允许的依赖仍被拒绝。

Xcode仍输出本机CoreSimulator版本落后的工具诊断，未启动任何模拟器，也没有以修补模拟器环境作为本轮任务。AppIntents缺少依赖而跳过元数据提取属于已有工具提示；最终编译告警按实际日志单列，不能把BUILD SUCCEEDED等同于日志完全无提示。

## 重入缺口补修与最终复验（2026-10-16）

前一轮“单操作准入已完成”的表述不完整。后续只读复核动态发现两处漏口：同步恢复未占用busy，允许restoreStarted回调启动第二项工作；setBusy在整体状态写完前发通知，旧收尾会覆盖重入新任务的文字和遮罩。本节记录用户批准后的实际补修，不把前一次全绿追认为已经覆盖这些场景。

修复行为：

- 同步手动备份、自动备份、替换前快照与恢复都先建立身份、占用准入，再进入实际步骤；作用域守卫覆盖成功／失败出口，且只释放自己持有的身份。同步恢复的文件步骤抽为私有方法，界面完成通知只在释放后发送。
- 异步恢复在准备回调之前占用准入；同步／异步恢复的restoreSyncCompleted均在释放busy之前完成，避免旧内部收尾处理通知回调刚启动的新恢复。
- busy、操作文字、遮罩和旧操作身份清理先整体提交，再发无参数属性通知。通知允许重入启动下一项工作，旧调用此后不再写旧状态。
- 同步完成消息在释放前保存，避免释放通知中的新工作改变本次要报告的错误。

新增三组数据驱动回归，共10项场景：同步／异步恢复在准备回调或restoreStarted中重入（4项）；同步手动／自动／替换前快照的准入及取消失败释放（3项）；busy／文字／遮罩通知中启动下一项工作（3项）。原实现构建成功后10项均断言失败，不是编译失败或测试框架超时；补修后全部通过。测试只操作临时数据库与INI，旧实现误启动的第二项worker停在入口检查点，清理时取消并放行，不并发触碰换库。
