# 062：服务单例迁移设计（A057）

日期：2026-10-17。状态：只冻结存量、不做迁移；门禁见 `tests/architecture_gate.py` 的 R9。

## 现状

`src/` 下有 21 个类声明 `static X* instance()`，调用约 548 处（不含 21 处定义），集中在 `DatabaseManager`（176）、`AppSettings`（70）、`TaskManager`（41）、`FocusTimer`（35）、`BackupService`（32）。QML 经 `QmlFacade::install` 以上下文属性取用，名单已由 `tests/QmlFacadeTests.cpp` 锁定。较新的对象已经走注入：`FocusSessionController`、`TaskInteractionCoordinator`、`PendingDeletion`、`TrayController`、`SyncController` 由 [SharedApp](../src/app/SharedApp.h) 构造、经 [AppServices](../src/app/AppServices.h) 暴露。

## 为什么不一次性迁移

单例之间互相调用，构造顺序和生命周期靠首次调用隐式决定；一次改几百处会同时改动启动顺序、测试装配和两个平台入口，回归面远大于收益。审计指出的问题是「没有约束，还在增加」，所以先冻结：R9 把现有 21 个类列成白名单，白名单外出现新的 `instance()` 声明就失败；白名单里的类去掉单例只提示从名单删除。

## 逐步迁移的顺序

1. 先迁 QML 不直接取用、只在服务内部传递的：`SystemMonotonicClock`（已有可注入的 `MonotonicClock` 接口，产品代码只在 `FocusTimer` 和 `SharedApp` 两处取默认实例）、`TrashNotifier`。
2. 再迁调用点少的业务服务（`PhaseSoundService`、`ShortcutRegistry`、`LogicalDayService`、`MemoService`、`TrashService`、`CountdownService` 等）：由 `SharedApp` 构造并持有，经 `AppServices` 交给需要它的服务和 `QmlFacade`。
3. `DatabaseManager`、`AppSettings`、`TaskManager`、`FocusTimer` 是枢纽，最后单独立项。
4. QML 侧上下文属性名不变，只换来源；`QmlFacadeTests` 的名单因此不用改。
